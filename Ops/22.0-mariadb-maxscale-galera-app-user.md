# Adding an Application User to MariaDB Galera Behind MaxScale

A complete record of how the application user (`appuser`) was created in the
3 node Galera cluster behind MaxScale, why each decision was made, how to
verify it works, and the best practices that should be applied when creating
application users in this architecture.

---

## 1. Environment

| Role | Hostname | IP | Notes |
|---|---|---|---|
| Application server | app | 10.10.10.180 | Connects to MaxScale, never to the databases directly |
| MaxScale | maxscale | 10.10.10.190 | Client entry point on port 4006 |
| Galera node 1 | mariadb-1 | 10.10.10.201 | |
| Galera node 2 | mariadb-2 | 10.10.10.202 | |
| Galera node 3 | mariadb-3 | 10.10.10.203 | |

Database name: `app_data`
Application user: `appuser`
Application password: `123` (lab value)

## 2. The key architectural fact: the database sees MaxScale, not the app

This is the single most important thing to understand when creating an
application user for this setup.

```
 App (10.10.10.180)  →  MaxScale (10.10.10.190:4006)  →  Galera node
                              ↑
                    the database sees THIS address
```

MariaDB's MaxScale documentation states it directly: because MaxScale sits
between the clients and the backend databases, **the backend databases will
see all clients as if they were connecting from MaxScale's address** .

This has a direct consequence for the `CREATE USER` statement: the host part
of the user definition must match **MaxScale's address** (or a pattern that
includes it), **not** the application server's address.

| Host pattern | Works? | Why |
|---|---|---|
| `'appuser'@'10.10.10.180'` | **No** | Database never sees `.180`; it sees `.190` |
| `'appuser'@'10.10.10.190'` | Yes | Exactly matches MaxScale's address |
| `'appuser'@'10.10.10.%'` | Yes | Covers the whole subnet, including `.190` |
| `'appuser'@'%'` | Yes | Covers every host |

For this setup, `'appuser'@'10.10.10.%'` was chosen. It covers MaxScale's
`.190` and is stricter than `%`.

## 3. What we did, step by step

### 3.1 Run the SQL on a Galera node, not through MaxScale

MaxScale is a proxy. It has no SQL engine and cannot execute `CREATE USER`,
`GRANT`, or `CREATE DATABASE`. These must be run on a database node.

Pick **one** Galera node, for example `.201`:

```bash
mariadb -u root -p
```

### 3.2 Create the database

```sql
CREATE DATABASE IF NOT EXISTS app_data;
```

**Galera behaviour:** `CREATE DATABASE` is a DDL statement. Galera replicates
DDL synchronously to every node. The documentation confirms that DDL
statements such as `CREATE USER` are replicated; only direct DML against
`mysql.*` tables (e.g. `INSERT INTO mysql.user`) is not .

So running this on one node is enough. All three nodes will have `app_data`
within the same transaction.

### 3.3 Create the user with the correct host pattern

```sql
CREATE USER 'appuser'@'10.10.10.%' IDENTIFIED BY '123';
```

**Why `10.10.10.%`:** the connection to the database comes from MaxScale's
address (`.190`), not from the application server (`.180`). The `10.10.10.%`
pattern covers `.190` and stays narrower than a full wildcard.

**MariaDB's own guidance on this:** the MaxScale documentation explains that
two sets of grants are usually required when MaxScale is involved, and that
**an alternative is to use one account with a wildcard host** which covers
both the client host and the MaxScale host . `10.10.10.%` is a
middle ground: it covers MaxScale and the rest of the subnet without opening
the account to every host on the internet.

### 3.4 Grant privileges on the application database only

```sql
GRANT ALL PRIVILEGES ON app_data.* TO 'appuser'@'10.10.10.%';
```

**Scope:** the grant is on `app_data.*`, not `*.*`. The user can do anything
inside its own database and nothing outside it.

**About `ALL PRIVILEGES`:** this was used because it is a lab and the
application needs to create tables. In production, this should be narrowed
(see Section 5). The important part is that the **scope** is `app_data.*`,
not `*.*`. A global `GRANT ALL ON *.*` would let the application user read
`mysql.user`, drop other databases, and create new users — which it should
never be able to do.

### 3.5 Flush privileges

```sql
FLUSH PRIVILEGES;
```

**Why:** `GRANT` normally takes effect immediately, but `FLUSH PRIVILEGES`
forces MariaDB to reload the grant tables from disk. It is safe to run and
removes any doubt that the new user is active.

### 3.6 Reload MaxScale's cached user list

On the MaxScale host:

```bash
maxctrl reload service Read-Write-Service
```

**Why:** MaxScale does not query the database for every client login. It
loads the user list from the backend and caches it. When a new user is
created, MaxScale does not know about it until it refreshes. MaxScale does
refresh automatically when an authentication fails, but the refresh is rate
limited, so an immediate retry may still fail .

`maxctrl reload service Read-Write-Service` forces the refresh immediately,
so the new user works on the first attempt.

## 4. Full sequence, copy-paste ready

Run **on any one Galera node** (e.g. `.201`, as root):

```sql
CREATE DATABASE IF NOT EXISTS app_data;
CREATE USER 'appuser'@'10.10.10.%' IDENTIFIED BY '123';
GRANT ALL PRIVILEGES ON app_data.* TO 'appuser'@'10.10.10.%';
FLUSH PRIVILEGES;
```

Run **on the MaxScale host**:

```bash
maxctrl reload service Read-Write-Service
```

Test **from the application server** (`.180`):

```bash
mariadb -h 10.10.10.190 -P 4006 -u appuser -p123 -e "SHOW DATABASES;"
```

`app_data` must appear in the output.

## 5. Verification

Run these checks in order. Each answers a different question.

### 5.1 Does the user exist on every Galera node?

On `.201`:

```sql
SELECT user, host FROM mysql.user WHERE user='appuser';
```

Expected: one row, `appuser | 10.10.10.%`.

On `.202` and `.203`, run the same query. The row must be present on all
three nodes. If it is missing on any node, Galera did not replicate the DDL,
which indicates a cluster problem, not a user-creation problem.

### 5.2 Are the grants correct?

```sql
SHOW GRANTS FOR 'appuser'@'10.10.10.%';
```

Expected:

```
GRANT USAGE ON *.* TO `appuser`@`10.10.10.%` IDENTIFIED BY PASSWORD '*...'
GRANT ALL PRIVILEGES ON `app_data`.* TO `appuser`@`10.10.10.%`
```

The second line is the one that matters. The scope must be `app_data.*`.

### 5.3 Does the login work directly against a node from MaxScale's host?

From the MaxScale host (`.190`):

```bash
mariadb --skip-ssl -h 10.10.10.201 -u appuser -p123 -e "SHOW DATABASES;"
```

`app_data` must appear. This proves the user and password work when the
connection comes from `.190`, which is the address the database will
actually see.

### 5.4 Does the login work **through** MaxScale?

From the application server (`.180`):

```bash
mariadb -h 10.10.10.190 -P 4006 -u appuser -p123 -e "SHOW DATABASES;"
```

`app_data` must appear. If step 5.3 works but this step fails with
`Access denied`, the MaxScale user cache is stale. Run:

```bash
maxctrl reload service Read-Write-Service
```

and retry.

### 5.5 Does read/write routing actually work?

Through MaxScale:

```bash
mariadb -h 10.10.10.190 -P 4006 -u appuser -p123
```

```sql
USE app_data;
CREATE TABLE IF NOT EXISTS notes (id INT AUTO_INCREMENT PRIMARY KEY, txt VARCHAR(50));
INSERT INTO notes (txt) VALUES ('through maxscale to galera');
SELECT * FROM notes;
```

The `CREATE`, `INSERT`, and `SELECT` must all succeed. The write goes to
the node MaxScale designates as `Master`, the read goes to a `Slave` node,
and Galera keeps all three in sync.

### 5.6 Is the data actually on the other nodes?

On `.202`:

```sql
SELECT * FROM app_data.notes;
```

The row must be present. That proves the write reached the cluster and was
replicated.

## 6. Best practices for application users in this architecture

### 6.1 Use the correct host pattern

This is the most common mistake. The pattern must match **MaxScale's
address**, because that is who the database sees.

| Approach | Security | Recommended for |
|---|---|---|
| `'appuser'@'10.10.10.190'` | Tightest | Production, when MaxScale's IP is fixed |
| `'appuser'@'10.10.10.%'` | Good | This setup; covers MaxScale without opening to all hosts |
| `'appuser'@'%'` | Least tight | Lab convenience only |

MariaDB's documentation acknowledges that wildcard hosts are a valid
alternative to maintaining duplicate accounts for the client host and the
MaxScale host . Choose the narrowest pattern that still covers
MaxScale.

### 6.2 Never use `GRANT ALL` in production

Security hardening guidance for MariaDB is explicit: **NEVER use `GRANT ALL`
in production environments**; instead, grant only the specific privileges
required for each user's role .

For a typical application, that means:

```sql
-- Production: minimal privileges for an application
GRANT SELECT, INSERT, UPDATE, DELETE
  ON app_data.* TO 'appuser'@'10.10.10.%';
```

Add `CREATE`, `DROP`, `INDEX`, and `ALTER` only if the application performs
schema changes:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, INDEX, ALTER
  ON app_data.* TO 'appuser'@'10.10.10.%';
```

The `ALL PRIVILEGES` used in this lab is acceptable for testing but should
be narrowed before the application goes live.

### 6.3 Keep the grant scope database-specific

Avoid global privileges (`ON *.*`) unless absolutely necessary. Guidance for
Galera clusters specifically recommends: **avoid granting global privileges
unless necessary; prefer database-specific privileges for application
users** .

`GRANT ... ON app_data.*` is correct. `GRANT ... ON *.*` would let the
application user read `mysql.user`, drop other databases, or create new
users — none of which an application should do.

### 6.4 Create the user on one node and let Galera replicate

You do **not** need to run `CREATE USER` and `GRANT` on all three nodes.
Galera replicates DDL synchronously. The MariaDB Galera documentation
confirms that DDL statements such as `CREATE USER` are replicated, while
direct DML against `mysql.*` tables is not .

Use `CREATE USER`, not `INSERT INTO mysql.user`. The latter is DML and will
**not** replicate across the cluster.

### 6.5 Reload MaxScale after creating or changing a user

MaxScale caches the user list. After any `CREATE USER`, `ALTER USER`, or
`GRANT`, run:

```bash
maxctrl reload service Read-Write-Service
```

MaxScale can also refresh on authentication failure, but the refresh is rate
limited, so an immediate retry may still fail .
Reloading explicitly avoids the confusing first-attempt failure.

### 6.6 Use a strong password outside the lab

`123` is a lab value. In production:

- Use a long, random password.
- Consider enabling MariaDB's password validation plugins
  (`simple_password_check`, `cracklib_password_check`) to enforce complexity
  .
- Store the password in the application's secret manager, not in source
  control.

### 6.7 Keep the application user separate from the monitor user

The `max` user is for MaxScale monitoring. The `appuser` is for the
application. Do not reuse one for the other.

| User | Purpose | Privileges |
|---|---|---|
| `max` | MaxScale monitor and service | `REPLICA MONITOR`, `SELECT ON mysql.*`, failover grants |
| `appuser` | Application through MaxScale | CRUD on `app_data.*` only |

The application should never log in as `max`, and the monitor should never
log in as `appuser`.

### 6.8 Audit and rotate

- Periodically check `SELECT user, host FROM mysql.user;` for unused
  accounts and drop them.
- Rotate the application password periodically:
  ```sql
  ALTER USER 'appuser'@'10.10.10.%' IDENTIFIED BY 'new_password';
  ```
  then reload MaxScale.

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `Access denied for user 'appuser'@'10.10.10.190'` even though the user exists | Host pattern does not match MaxScale's address | Check `SELECT user, host FROM mysql.user WHERE user='appuser';`. Use `10.10.10.%` or `10.10.10.190`, not `10.10.10.180` |
| `Access denied` on the first attempt, then works on retry | MaxScale's user cache was stale | Run `maxctrl reload service Read-Write-Service` |
| `SHOW DATABASES` through MaxScale does not list `app_data` | Grant is on the wrong scope | `SHOW GRANTS FOR 'appuser'@'10.10.10.%';` must show `ON \`app_data\`.*` |
| User exists on `.201` but not on `.202` | Galera did not replicate the DDL | Check `wsrep_cluster_size` and `wsrep_ready` on all nodes; the cluster must be healthy before DDL replicates |
| `ERROR 1396 (HY000): Operation CREATE USER failed` | The user already exists with that host pattern | `DROP USER 'appuser'@'10.10.10.%';` then recreate, or use `CREATE USER IF NOT EXISTS` (MariaDB 10.1+) |
| `ERROR 1064` on `DROP USER ... IDENTIFIED BY` | `DROP USER` does not accept `IDENTIFIED BY` | Use `DROP USER 'appuser'@'10.10.10.%';` with no password clause |
| `CREATE USER` on one node does not appear on others | The cluster is not healthy, or `INSERT INTO mysql.user` was used instead of `CREATE USER` | Verify `wsrep_cluster_size = 3`; use `CREATE USER`, not direct DML |

## 8. Summary

| Step | Where | Command |
|---|---|---|
| 1 | Any Galera node | `CREATE DATABASE IF NOT EXISTS app_data;` |
| 2 | Same node | `CREATE USER 'appuser'@'10.10.10.%' IDENTIFIED BY '123';` |
| 3 | Same node | `GRANT ALL PRIVILEGES ON app_data.* TO 'appuser'@'10.10.10.%';` |
| 4 | Same node | `FLUSH PRIVILEGES;` |
| 5 | MaxScale host | `maxctrl reload service Read-Write-Service` |
| 6 | App server | `mariadb -h 10.10.10.190 -P 4006 -u appuser -p123` |

The host pattern must match **MaxScale's address**, because that is who the
database sees. The grant scope must be **`app_data.*`**, not `*.*`. Galera
replicates the DDL from one node. MaxScale must be told to reload its cached
user list.

For production, replace `ALL PRIVILEGES` with the specific privileges the
application needs, and replace `123` with a strong password.
