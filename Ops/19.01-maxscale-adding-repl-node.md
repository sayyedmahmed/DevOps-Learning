# MaxScale — Adding a Replica Node

A beginner-friendly guide to taking a single-server MaxScale setup and
adding a second database as a replica, including why each configuration
line exists and every problem encountered along the way.

---

## Part 1 — The Big Picture

### What we are building

**Before:**

```
App --> MaxScale (10.10.10.190:4006) --> mariadb-1 (10.10.10.201)
```

**After:**

```
App --> MaxScale (10.10.10.190:4006) --+--> mariadb-1 (10.10.10.201)  primary
                                       |
                                       +--> mariadb-2 (10.10.10.202)  replica
```

The application still connects to **one address** — MaxScale's. It never
knows there are two servers behind it. MaxScale decides where each query
goes:

- **Writes** (`INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`) → primary
- **Reads** (`SELECT` outside a transaction) → replica
- **Anything inside a transaction** → primary

### What MaxScale can and cannot do

MaxScale can **see** that a server is a replica. It cannot **create**
replication. You must set up MariaDB replication yourself first. MaxScale
only watches and routes.

> **Key idea:** MaxScale is a traffic director, not a replication setup
> tool. Step order matters: replication first, MaxScale second.

## Part 2 — Prepare the New Server (mariadb-2, 10.10.10.202)

### 2.1 Install MariaDB

```bash
sudo dnf install mariadb-server -y
sudo systemctl enable --now mariadb
```

### 2.2 Configure the server file

```bash
sudo vim /etc/my.cnf.d/mariadb-server.cnf
```

Under `[mysqld]`:

```ini
bind-address      = 0.0.0.0
server_id         = 2
log_bin           = mariadb-bin
binlog_format     = ROW
log_slave_updates = ON
read_only         = ON
report_host       = 10.10.10.202
```

**Why each setting exists:**

| Setting | Why it is required |
|---|---|
| `bind-address = 0.0.0.0` | Without this, MariaDB listens only on `127.0.0.1` and MaxScale (on another machine) cannot reach it |
| `server_id = 2` | Every server in a replication cluster must have a **unique** `server_id`. Two servers with the same ID causes replication corruption. Primary has `1`, replica must have `2` |
| `log_bin = mariadb-bin` | Records every change on this server so other servers could replicate from it later (needed if this replica ever becomes primary) |
| `binlog_format = ROW` | Safest format for replication. Records the actual data changed, not the SQL statement |
| `log_slave_updates = ON` | Allows this replica to pass on changes it received from the primary. Needed if this replica is promoted to primary later |
| `read_only = ON` | Blocks normal users from writing directly to the replica. Prevents accidental writes that would break replication |
| `report_host = 10.10.10.202` | Shows the replica's real IP in replication status |

```bash
sudo systemctl restart mariadb
```

### 2.3 Open the firewall

```bash
sudo firewall-cmd --permanent --add-port=3306/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --list-ports        # must show 3306/tcp
```

**Why:** MaxScale connects to this server from the network. Without this
rule, the TCP connection is dropped before MariaDB even sees it.

### 2.4 Verify the server is listening on all interfaces

```bash
ss -tlnp | grep 3306
```

Must show `0.0.0.0:3306`, not `127.0.0.1:3306`. If it shows `127.0.0.1`,
`bind-address` did not take effect — restart MariaDB again.

## Part 3 — Set Up Replication (MariaDB level, before touching MaxScale)

MaxScale only discovers replication. You must create it.

### 3.1 On the primary (mariadb-1, 201), create a replication user

```sql
CREATE USER 'repl'@'10.10.10.%' IDENTIFIED BY '123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.10.10.%';
```

**Why:** the replica logs in with this account to read the primary's
binary log. `REPLICATION SLAVE` is the minimum privilege for that.

### 3.2 On the primary, note its current binlog position

```sql
SHOW MASTER STATUS;
```

Example output:

```
+--------------------+----------+--------------+------------------+
| File               | Position | Binlog_Do_DB | Binlog_Ignore_DB |
+--------------------+----------+--------------+------------------+
| mariadb-bin.000005 |     1051 |              |                  |
+--------------------+----------+--------------+------------------+
```

Note `File` and `Position` — you will need them on the replica.

### 3.3 On the replica (mariadb-2, 202), point it at the primary

```sql
STOP SLAVE;
RESET SLAVE ALL;

CHANGE MASTER TO
  MASTER_HOST='10.10.10.201',
  MASTER_USER='repl',
  MASTER_PASSWORD='123',
  MASTER_LOG_FILE='mariadb-bin.000005',
  MASTER_LOG_POS=1051,
  MASTER_USE_GTID=no;

START SLAVE;
SHOW SLAVE STATUS\G
```

**Why each line:**

| Line | Reason |
|---|---|
| `STOP SLAVE; RESET SLAVE ALL;` | Clears any previous replication config, so you start clean |
| `MASTER_HOST` | Must be **exactly** the same string the MaxScale config uses for the primary. If MaxScale says `10.10.10.201` and replication says the hostname, MaxScale cannot match them |
| `MASTER_USER` / `MASTER_PASSWORD` | The account from step 3.1 |
| `MASTER_LOG_FILE` / `MASTER_LOG_POS` | Where to start reading the primary's binary log |
| `MASTER_USE_GTID=no` | Use file/position replication (explained below) |

Both `Slave_IO_Running` and `Slave_SQL_Running` must say **Yes**.

### 3.4 The GTID choice — important

There are two ways MariaDB can track replication position:

| Method | How it works | MaxScale failover support |
|---|---|---|
| **File/position** (`MASTER_USE_GTID=no`) | "Read from file X at byte Y" | ❌ **Does not work** |
| **GTID** (`MASTER_USE_GTID=slave_pos`) | "Read every transaction I have not seen yet" | ✅ Required |

MaxScale's `auto_failover` **requires GTID**. If you use file/position
replication, MaxScale can still route reads/writes to the replica, but it
**cannot promote the replica automatically** when the primary dies.

For this guide we will switch to GTID later so failover works. If you are
only interested in read/write splitting, file/position is fine.

## Part 4 — Add the Replica to MaxScale

The replica is replicating. Now tell MaxScale it exists.

### Option A — Live, no restart (recommended)

On MaxScale (190):

```bash
maxctrl create server mariadb-2 10.10.10.202 3306
maxctrl link monitor MariaDB-Monitor mariadb-2
```

Two commands. That is all.

- `create server` — creates the new server object
- `link monitor` — tells the monitor to watch it

You do **not** edit `Read-Write-Service`. It uses `cluster=MariaDB-Monitor`,
which means "use whatever servers the monitor watches." So adding the
server to the monitor automatically makes it part of the service.

### Option B — Edit the file (needs a restart)

In `/etc/maxscale.cnf`, add a new section:

```ini
[mariadb-2]
type=server
address=10.10.10.202
port=3306
```

Change the monitor's server list:

```ini
[MariaDB-Monitor]
servers=mariadb-1,mariadb-2
```

Then:

```bash
sudo -u maxscale maxscale --config-check
sudo systemctl restart maxscale
```

**Use only one method.** Using both creates the server object twice and
breaks MaxScale.

### What changed in the config (comparison)

```
Before (1 server)                  After (2 servers)
[mariadb-1] type=server            [mariadb-1] type=server
                                   [mariadb-2] type=server           <-- new
servers=mariadb-1                  servers=mariadb-1,mariadb-2       <-- changed
cluster=MariaDB-Monitor            cluster=MariaDB-Monitor           <-- unchanged
port=4006                          port=4006                          <-- unchanged
```

**Only the monitor's server list changed.** The service and listener are
untouched. Clients keep using the same address.

## Part 5 — Create the MaxScale User on the Replica

The monitor logs in to **every** server in `servers=`. The `max` user must
exist on the replica with the same grants and password as on the primary.

With **file/position replication**, users created on the primary **before**
the replication starting position are **not** replayed. The `max` user was
created on the primary earlier, so it does not appear on the replica. You
must create it manually.

On the replica (202):

```sql
CREATE USER 'max'@'10.10.10.%' IDENTIFIED BY '123';
GRANT REPLICA MONITOR ON *.*             TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.user               TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.global_priv        TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.db                 TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.tables_priv        TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.columns_priv       TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.proxies_priv       TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.roles_mapping      TO 'max'@'10.10.10.%';
GRANT SHOW DATABASES ON *.*              TO 'max'@'10.10.10.%';

-- Required later for automatic failover (see Part 9)
GRANT RELOAD, PROCESS, SHOW DATABASES, EVENT, SET USER, READ_ONLY ADMIN
  ON *.* TO 'max'@'10.10.10.%';
GRANT REPLICATION SLAVE ADMIN, BINLOG ADMIN, CONNECTION ADMIN
  ON *.* TO 'max'@'10.10.10.%';

FLUSH PRIVILEGES;
```

**Why each grant group:**

| Group | What it allows |
|---|---|
| `REPLICA MONITOR` | Read replication status (`SHOW SLAVE STATUS`) |
| `SELECT ON mysql.*` | Read the account list so MaxScale can authenticate clients |
| `RELOAD, PROCESS, SHOW DATABASES, EVENT, SET USER, READ_ONLY ADMIN` | Change server state during failover |
| `REPLICATION SLAVE ADMIN, BINLOG ADMIN, CONNECTION ADMIN` | Run `STOP SLAVE`, `CHANGE MASTER` during failover |

Without the last two grant groups, failover **will fail** with
`Access denied; you need (at least one of) the SUPER, REPLICATION SLAVE ADMIN privilege(s)`.

Verify:

```sql
SELECT user, host FROM mysql.user WHERE user='max';
```

There must be exactly **one** row per host pattern. If you also see
`'max'@'10.10.10.190'`, the most-specific host wins and MariaDB may
authenticate against the wrong row.

## Part 6 — Monitor Configuration

The monitor block in `/etc/maxscale.cnf`:

```ini
[MariaDB-Monitor]
type=monitor
module=mariadbmon
servers=mariadb-1,mariadb-2
user=max
password="123"
monitor_interval=2s
failcount=5
replication_user=repl
replication_password="123"
auto_failover=true
auto_rejoin=true
```

**Why each option:**

| Option | What it does |
|---|---|
| `servers=` | Every database MaxScale watches. Add each server name here (or via `maxctrl link monitor`) |
| `user` / `password` | The account the monitor logs in with. **Quotes around the password are required** — `123` without quotes is parsed as a number and dropped |
| `monitor_interval` | How often to check each server's health. `2s` means a stopped server is noticed in ≤2s |
| `failcount` | How many consecutive failed checks before a server is declared dead. `5 × 2s = 10s` |
| `replication_user` / `replication_password` | Used by MaxScale to reconfigure replication during failover or rejoin |
| `auto_failover` | Promote a replica automatically if the primary stays down longer than `failcount × monitor_interval` |
| `auto_rejoin` | Bring the old primary back as a replica after it recovers |

**Option names use underscores.** `autofailover` and `autorejoin` are
silently ignored. `ture` is not a valid boolean.

## Part 7 — Verify

### 7.1 MaxScale sees both servers correctly

On MaxScale (190):

```bash
mariadb --skip-ssl -h 10.10.10.202 -u max -p123 -e "SELECT 1"
```

Must return `1`. Then:

```bash
maxctrl list servers
```

Expected:

```
│ mariadb-1 │ 10.10.10.201 │ 3306 │ 0 │ Master, Running │ ... │
│ mariadb-2 │ 10.10.10.202 │ 3306 │ 0 │ Slave, Running  │ ... │
```

`Slave, Running` means MaxScale saw replication working and assigned the
role itself.

### 7.2 Replication actually works

Create a table on **both** servers, then write on the primary and check
the replica.

On **db2 (202)**:

```sql
CREATE DATABASE IF NOT EXISTS test;
USE test;
CREATE TABLE IF NOT EXISTS notes (id INT AUTO_INCREMENT PRIMARY KEY, txt VARCHAR(50));
```

On **db1 (201)**:

```sql
USE test;
INSERT INTO test.notes (txt) VALUES ('replication check from primary');
```

On **db2 (202)**:

```sql
SELECT * FROM test.notes WHERE txt = 'replication check from primary';
```

If the row appears → replication works end to end.

### 7.3 Read/write splitting

New client connection through MaxScale:

```bash
mariadb -h 10.10.10.190 -P 4006 -u appuser -p
```

```sql
USE test;
SELECT @@hostname;            -- replica (db2)
START TRANSACTION;
SELECT @@hostname;            -- primary (db1)
COMMIT;
INSERT INTO test.notes (txt) VALUES ('split test');
SELECT * FROM test.notes;     -- reads from replica
```

Give db1 and db2 different hostnames so the split is visible.

## Part 8 — Making Failover Work (GTID switch)

If you set up replication with `MASTER_USE_GTID=no` (file/position),
automatic failover will not work. Switch the replica to GTID:

On **db2 (202)**:

```sql
STOP SLAVE;
RESET SLAVE ALL;

CHANGE MASTER TO
  MASTER_HOST='10.10.10.201',
  MASTER_USER='repl',
  MASTER_PASSWORD='123',
  MASTER_USE_GTID=slave_pos;

START SLAVE;
SHOW SLAVE STATUS\G
```

The only difference from before is `MASTER_USE_GTID=slave_pos` replacing
`MASTER_LOG_FILE` + `MASTER_LOG_POS`. **No data changes** — this only
changes how the replica tracks its position.

Verify:

```
Using_Gtid: Slave_Pos
Slave_IO_Running: Yes
Slave_SQL_Running: Yes
```

`Slave_Pos` (not `No`) means MaxScale can now use GTID for failover.

Restart MaxScale to apply:

```bash
sudo systemctl restart maxscale
sleep 5
maxctrl list servers
```

### Testing failover

On db1 (201):

```bash
sudo systemctl stop mariadb
```

On MaxScale (190):

```bash
watch -n 1 maxctrl list servers
```

Within ~10 seconds (`failcount × monitor_interval`) `mariadb-2` should
become `Master, Running` and `mariadb-1` should show `Down`.

Bring db1 back:

```bash
sudo systemctl start mariadb
```

With `auto_rejoin=true`, db1 should return as `Slave, Running` of db2.

## Part 9 — Issues Encountered and Their Fixes

This section records every problem met while adding the replica, so the
next person does not have to re-debug.

### 9.1 `Auth Error, Down` in `maxctrl list servers`

**Symptom:** `maxctrl list servers` shows `Auth Error, Down` even though
`mariadb --skip-ssl -h 10.10.10.201 -u max -p` works from the shell.

**Cause:** MaxScale logs in with the same credentials, but MaxScale's
`mariadbmon` runs a specific set of queries. If any required grant is
missing, MariaDB rejects the login and MaxScale reports `Auth Error`.

**Fix:** verify the grants on the server actually used by MaxScale
(`SHOW GRANTS FOR 'max'@'10.10.10.%';`) and confirm the password matches
(`authentication_string` for password `123` is
`*23AE809DDACAF96AF0FD78ED04B6A265E05AA257`).

### 9.2 `Access denied … (using password: NO)`

**Symptom:** MaxScale log shows `Access denied for user 'max'@'…' (using
password: NO)`.

**Cause:** the monitor never sent a password. Several things can cause
this:

| Sub-cause | Fix |
|---|---|
| `password=123` in the config parsed as an integer and dropped | Use `password="123"` (quoted string) |
| `.secrets` file present → encrypted-password mode → plaintext value fails to decrypt | Move `/var/lib/maxscale/.secrets` aside, or run `maxpasswd 123` and paste the hex into `password=` |
| `maxctrl alter monitor … password=123` rejected with `Expected a json string, but got a json integer` | Use `password='"123"'` on the command line |

**The `.secrets` issue in detail:** if `/var/lib/maxscale/.secrets`
exists, MaxScale treats every `password=` as an **encrypted** value. A
plaintext `"123"` cannot be decrypted, so MaxScale ends up sending no
password. Either delete `.secrets` (plaintext mode) or encrypt the
password with `maxpasswd` and paste the resulting hex string into the
config.

### 9.3 Duplicate `max` user

**Symptom:** grants look correct, yet login fails.

**Cause:** MariaDB had two rows — `'max'@'10.10.10.190'` and
`'max'@'10.10.10.%'`. MariaDB matches the **most specific host first**, so
MaxScale (from `10.10.10.190`) authenticated against the `.190` row, which
had different or missing grants.

**Fix:** drop the specific-IP row:

```sql
DROP USER 'max'@'10.10.10.190';
FLUSH PRIVILEGES;
```

### 9.4 `ERROR 2026 (HY000): SSL is required, but the server does not support it`

**Symptom:** connecting with `mariadb` (no flags) fails, but `--skip-ssl`
works.

**Cause:** the MariaDB client on the MaxScale host defaults to requiring
TLS, but the server has no certificates configured. MaxScale's monitor
uses the same client library and hits the same wall.

**Fix (lab):** disable the client's TLS requirement:

```bash
sudo tee /etc/my.cnf.d/zz-no-ssl.cnf >/dev/null <<'EOF'
[client]
ssl=0
EOF
```

**Fix (production):** add `ssl_cert` and `ssl_key` to `[mysqld]` on the
server so TLS is available. Never disable TLS in production.

### 9.5 `ERROR 2002 (HY000): Can't connect to server … (115)`

**Symptom:** connection from MaxScale times out with errno 115.

**Cause:** TCP-level reachability problem — the packet never reaches the
server. MariaDB may be running and listening, but the firewall, a route,
or an interface configuration is blocking the path.

**Diagnostic:**

```bash
# on the MaxScale host
ping -c 2 10.10.10.202
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/10.10.10.202/3306' && echo OPEN || echo BLOCKED
ip neigh show 10.10.10.202

# on the server
ss -tlnp | grep 3306
sudo firewall-cmd --list-all
ip -4 addr show
ip route get 10.10.10.190        # src must equal the server's address
```

**Common fixes:**

- `bind-address` set to `127.0.0.1` → change to `0.0.0.0`
- `firewall-cmd --list-ports` empty → add `3306/tcp`
- ARP fails (`ip neigh` shows `FAILED`) → the server's IP is not on the
  interface expected. Confirm the static IP is really assigned.

### 9.6 Missing database and table on the replica

**Symptom:** `test` database missing on db2, but replication appears
healthy.

**Cause:** file/position replication only replays events **from the
starting position onward**. Objects created on the primary before that
position (`CREATE DATABASE test`, `CREATE USER 'max'`) are never
replayed.

**Fix:** create the missing objects on the replica manually, or take a
fresh dump from the primary and start replication from the position
recorded in the dump. Switching to GTID avoids the issue entirely
because GTID replays the full history.

### 9.7 `Got fatal error 1236 … binlog truncated`

**Symptom:** replica fails with `Got fatal error 1236 from master when
reading data from binary log: 'binlog truncated in the middle of event'`.

**Cause:** the replica pointed at an old binlog file that had been
truncated or rotated away on the primary.

**Fix:** reset replication and point at the primary's current position:

```sql
STOP SLAVE;
RESET SLAVE ALL;
CHANGE MASTER TO
  MASTER_HOST='10.10.10.201',
  MASTER_USER='repl',
  MASTER_PASSWORD='123',
  MASTER_LOG_FILE='<current file from SHOW MASTER STATUS>',
  MASTER_LOG_POS=<current position>,
  MASTER_USE_GTID=no;
START SLAVE;
```

Transactions between the old broken position and the new position are
not replayed. For a fresh replica with no important data this is
acceptable.

### 9.8 Typos in monitor options

**Symptom:** failover never triggers despite being "enabled".

**Cause:** `autofailover=ture` and `autorejoin=true` in the config.

**Fix:** the correct names are `auto_failover=true` and `auto_rejoin=true`.
Option names use underscores and booleans are `true` / `false` (not `ture`).

Verify with:

```bash
maxctrl show monitor MariaDB-Monitor | grep -iE 'auto_failover|auto_rejoin'
```

### 9.9 `Failed to stop replica connection on 'mariadb-2': Access denied; you need (at least one of) the SUPER, REPLICATION SLAVE ADMIN privilege(s)`

**Symptom:** failover starts — MaxScale selects `mariadb-2` and tries to
promote it — then fails:

```
Failed to stop replica connection on 'mariadb-2': Query
'SET STATEMENT max_statement_time=3 FOR STOP SLAVE' failed:
'Access denied; you need … SUPER, REPLICATION SLAVE ADMIN privilege(s)'
(1227). Failover 'mariadb-1' -> 'mariadb-2' failed.
```

**Cause:** the `max` user was granted only the **monitoring** privileges
(`REPLICA MONITOR`, `SELECT ON mysql.*`). To perform failover, MaxScale
must run `STOP SLAVE` and `CHANGE MASTER TO` on the replica, which require
`REPLICATION SLAVE ADMIN` (or `SUPER`) and related privileges. Without
them, MariaDB rejects the operation and failover aborts.

**Fix:** on the replica (and the primary too, for future rejoin), grant:

```sql
GRANT RELOAD, PROCESS, SHOW DATABASES, EVENT, SET USER, READ_ONLY ADMIN
  ON *.* TO 'max'@'10.10.10.%';
GRANT REPLICATION SLAVE ADMIN, BINLOG ADMIN, CONNECTION ADMIN
  ON *.* TO 'max'@'10.10.10.%';
FLUSH PRIVILEGES;
```

Then restart the monitor so it reloads the new privileges:

```bash
maxctrl stop monitor MariaDB-Monitor
maxctrl start monitor MariaDB-Monitor
```

Failover will now proceed within `failcount × monitor_interval` seconds.

## Part 11 — Rules to Remember

1. **Replication first, MaxScale second.** MaxScale sees replication; it does not create it.
2. **`max` user on every server** in `servers=`, with identical grants and password.
3. **Quote passwords.** `"123"` is a string; `123` is a number and gets dropped.
4. **One `max` user per host pattern.** Duplicates cause MariaDB to match the wrong one.
5. **`.secrets` + plaintext password = failure.** Either remove `.secrets` or use `maxpasswd`.
6. **`MASTER_HOST` must match the MaxScale address exactly** — no hostname/IP mixing.
7. **GTID is required for `auto_failover`.** File/position replication works for splitting but not for failover.
8. **Monitor grants ≠ failover grants.** `REPLICA MONITOR` reads state; `REPLICATION SLAVE ADMIN` changes it.
9. **`failcount × monitor_interval` is the failover delay.** `5 × 2s = 10s` by default.
10. **The application never changes.** It always uses MaxScale's address and port.
```
