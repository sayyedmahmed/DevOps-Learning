# P1.2 - Failover Recovery & Automatic Cleanup Guide

## 1. The Scenario: What Happens When a Node Dies?

Imagine `db-node1` is running MySQL and suddenly loses power or crashes. You check the cluster on `db-node2`, and you see this:

*   `Online: [ db-node2 ]`
*   `OFFLINE: [ db-node1 ]`
*   `webdb-group`: **Stopped**

### Why are resources "Stopped" instead of moving?
By default, Pacemaker is "sticky." It remembers that MySQL was last running on `db-node1`. When `db-node1` goes offline, Pacemaker waits for it to come back rather than immediately moving everything to `db-node2`. This prevents unnecessary moving if the node just had a quick network blip.

---

## 2. How to Fix It Manually (The "Force Start" Method)

If `db-node1` is definitely down and you want MySQL running on `db-node2` right now, use one of these commands on **db-node2**.

### Option A: Clear Constraints (Recommended)
This tells Pacemaker: "Forget where it was last running. Just start it wherever it can."

```bash
pcs resource cleanup webdb-group
```
*Wait about 60–90 seconds.* Pacemaker will realize `db-node1` is gone and start the group on `db-node2`.

### Option B: Force Move
This explicitly tells Pacemaker: "Move everything to `db-node2` right now."

```bash
pcs resource move webdb-group db-node2
```

---

## 3. Verification: Did It Work?

After waiting a minute, check the status on **db-node2**:

```bash
pcs status
```

**Expected Result:**
*   `webdb-group`: **Started** on `db-node2`
*   `vip-db`: Started on `db-node2`

**Test from your Client VM (`db-node` / `10.10.10.101`):**
```bash
mysql -h 10.10.10.130 -u root -p123 -e "SELECT @@hostname;"
```
**Expected Output:**
```text
+------------+
| @@hostname |
+------------+
| db-node2   |
+------------+
```

## 4. Troubleshooting: Checking Logs

If resources fail to start or behave unexpectedly, you must check the logs to see why.

### Check MySQL Error Log (Most Important)
This tells you if MySQL failed due to permissions, missing files, or NFS locks.
Run on the node where MySQL is trying to start:
```bash
tail -n 50 /var/log/mysql/error.log
```
*Look for:* `[ERROR]` lines, specifically `Unable to lock ./ibdata1` (NFS lock issue).

### Check Pacemaker/Cluster Logs
This tells you if Pacemaker failed to execute a command or if there were communication issues.
Run on any node:
```bash
journalctl -u pacemaker -n 50 --no-pager
```

### Check Corosync Connectivity
This tells you if the nodes can still talk to each other.
Run on any node:
```bash
corosync-cfgtool -s
```
*Look for:* `status: connected` for the other node.

## 5. Common Problem: The "NFS Lock" Delay

Sometimes, even after you run `cleanup`, MySQL fails to start with an error like:
`Unable to lock ./ibdata1 error: 11`

### Why?
When `db-node1` crashed, it didn't have time to tell the NFS server "I'm done." The NFS server holds onto the file locks for about **90 seconds** to protect the data. If MySQL tries to start during those 90 seconds, it sees the lock and fails.

### The Fix:
1.  **Wait 2 minutes.** Let the NFS lock expire naturally.
2.  Run `pcs resource cleanup p_mysql` again.
3.  If it still fails, check the logs: `tail -n 20 /var/log/mysql/error.log`.

---

## 6. How to Make It Automatic (No More Manual Cleanup!)

You can tell Pacemaker to be smarter so you don't have to run `cleanup` every time. Run this on **db-node1** (or whichever node is currently active):

```bash
pcs resource update p_mysql meta failure-timeout=60s migration-threshold=3
```

### What this does:
*   `failure-timeout=60s`: If MySQL fails (e.g., because of an NFS lock), Pacemaker waits 60 seconds and then **automatically clears the error** and tries again.
*   `migration-threshold=3`: It will try to restart on the same node up to 3 times. Only after 3 failures will it give up and move the whole group to the other node.

**Result:** If a node crashes, Pacemaker will wait for the NFS locks to clear and restart MySQL automatically on the new node without you touching anything.

---

## 7. Bringing the Dead Node Back

Once you power `db-node1` back on:
1.  It will rejoin the cluster automatically.
2.  Resources will likely stay on `db-node2` because of "stickiness."
3.  If you want to move them back to `db-node1`:

```bash
pcs resource move webdb-group db-node1
pcs resource clear webdb-group
```
