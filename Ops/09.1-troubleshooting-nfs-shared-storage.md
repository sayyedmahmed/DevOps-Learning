# 09.1 - MySQL NFS Shared Storage: Single-Node Setup and Verification

## 1. Purpose

This document records the single-node NFS shared storage setup, the permission problems encountered, the diagnosis, and the resolution.

It is intended to answer:

- What was configured?
- What failed?
- Why did it fail?
- What commands were used to diagnose it?
- What fixed the issue?
- How do we verify that MySQL can safely use the NFS-backed data directory?

> **Path note:** This document uses `/var/lib/mysql_data` as the MySQL data directory mounted directly from NFS.  
> If you are following an earlier example that uses `/mnt/shared/mysql_data`, keep the paths consistent and do not mix the two layouts.

| Item | Value |
|---|---|
| NFS server | `10.10.10.200` |
| NFS export | `/srv/nfs-dbstorage` |
| MySQL node | `db-node1` |
| MySQL node IP | `10.10.10.110` |
| MySQL data directory | `/var/lib/mysql_data` |
| NFS group | `nfsuser` |

| MySQL UID/GID | `27:27` |
| MySQL supplementary group | `nfsuser` / GID `1000` |
| NFS version | `4.2` |

---

## 3. Problem Observed

During the NFS shared storage setup, access to the shared directory was not working as expected.

Main symptoms:

- The `root` user on the database node could not access the NFS share normally.
- MySQL needed access to the shared directory.
- The shared directory had restrictive permissions.
- The NFS export used `root_squash`.
- Ownership of files inside the shared directory had to be corrected so the `mysql` user could read and write safely.

The important question was:

> Why could `root` not access the share, while the `mysql` user could after group membership and ownership corrections?

---

## 4. Root Cause

The issue was caused by a combination of NFS security behavior and Linux filesystem permissions.

### 4.1 NFS `root_squash`

The NFS export was configured with:

```text
root_squash
```

This means that when the client machine connects as `root`, the NFS server does not treat that request as real root. Instead, it maps the client `root` user to an unprivileged identity, usually something like `nfsnobody` or `nobody`.

So even if you are `root` on `db-node1`, the NFS server may not allow full privileged access to the exported directory.

### 4.2 Restrictive Directory Permissions

The NFS server directory had permissions similar to:

```text
drwxrws--- root nfsuser /srv/nfs-dbstorage
```

That means:

| Who | Permission |
|---|---|
| Owner `root` | read, write, enter directory |
| Group `nfsuser` | read, write, enter directory |
| Others | no access |

Because client `root` is squashed to an unprivileged user, it does not automatically get access as server `root`.

If the squashed identity is not the owner and is not in `nfsuser`, access is denied.

### 4.3 MySQL User Needed Group Access

The MySQL service runs as:

```text
mysql
```

with UID/GID:

```text
27:27
```

For MySQL to access the NFS share, the `mysql` user needed to belong to the shared group:

```text
nfsuser
```

with GID:

```text
1000
```

Expected MySQL identity:

```text
uid=27(mysql) gid=27(mysql) groups=27(mysql),1000(nfsuser)
```

### 4.4 Ownership of Existing Files

Even after the directory itself was accessible, existing files inside the shared directory could still have incorrect ownership.

If files were created by the wrong user or by a squashed identity, MySQL might not be able to read or write them.

The command that corrected this in the lab was:

```bash
chown -R mysql:nfsuser /var/lib/mysql_data
```

This recursively changed ownership of the mounted NFS data directory so that:

- Owner: `mysql`
- Group: `nfsuser`

---

## 5. Resolution Summary

| Issue | Cause | Fix | Verification |
|---|---|---|---|
| `root` denied access to NFS share | `root_squash` maps client root to unprivileged identity | Use the `mysql` user, not root, for application access | Test with `su -s /bin/bash -c 'ls -la /var/lib/mysql_data' mysql` |
| MySQL could not access shared directory | MySQL user not in `nfsuser` group | Add MySQL to `nfsuser` | `id mysql` |
| Shared directory inaccessible to non-owner | Permissions were `2770` | Ensure group `nfsuser` has access | `ls -ld /srv/nfs-dbstorage` |
| Existing files had wrong ownership | Files created by incorrect/squashed identity | `chown -R mysql:nfsuser /var/lib/mysql_data` | `ls -la /var/lib/mysql_data` |
| Mount not persistent | No `/etc/fstab` entry | Add NFS mount with `_netdev` | `findmnt --verify --verbose` |
| MySQL pointed to wrong datadir | `/etc/my.cnf` not updated | Set `datadir=/var/lib/mysql_data` | `SELECT @@datadir;` |

## 6. Step-by-Step Configuration and Verification

## 6.1 Verify NFS Server Configuration

Run these commands on the NFS server:

```bash
systemctl status nfs-server --no-pager
getent group nfsuser
ls -ld /srv/nfs-dbstorage
exportfs -v
```

Expected results:

```text
nfsuser:x:1000:
```

```text
drwxrws--- root nfsuser /srv/nfs-dbstorage
```

The export should include the database node IP and options similar to:

```text
/srv/nfs-dbstorage 10.10.10.110(rw,sync,root_squash,no_subtree_check)
```

The NFS export file used:

```text
/etc/exports.d/mysql_db.exports
```

Example content:

```text
/srv/nfs-dbstorage 10.10.10.110(rw,sync,no_subtree_check,root_squash)
```

Apply exports:

```bash
exportfs -rav
```

Verify:

```bash
exportfs -v
```

---

## 6.2 Verify MySQL User and Group on `db-node1`

Run on `db-node1`:

```bash
id mysql
getent group nfsuser
```

Expected:

```text
uid=27(mysql) gid=27(mysql) groups=27(mysql),1000(nfsuser)
```

```text
nfsuser:x:1000:
```

If MySQL is not in the `nfsuser` group, add it:

```bash
usermod -aG nfsuser mysql
```

Then verify again:

```bash
id mysql
```

> **Important:** The MySQL user must belong to the same numeric GID as the NFS server group. Username matching alone is not enough for NFS. UID/GID matching is what matters.

---

## 6.3 Mount NFS at the MySQL Data Directory

Create the mount point:

```bash
mkdir -p /var/lib/mysql_data
```

Mount the NFS export:

```bash
mount -t nfs4 -o hard,vers=4.2 \
  10.10.10.200:/srv/nfs-dbstorage /var/lib/mysql_data
```

Verify the mount:

```bash
findmnt -T /var/lib/mysql_data
```

Expected source:

```text
10.10.10.200:/srv/nfs-dbstorage
```

You can also check:

```bash
df -h /var/lib/mysql_data
mount | grep nfs
```

---

## 6.4 Configure Automatic Mounting

Edit `/etc/fstab`:

```bash
vi /etc/fstab
```

Add:

```fstab
10.10.10.200:/srv/nfs-dbstorage /var/lib/mysql_data nfs4 rw,hard,vers=4.2,_netdev 0 0
```

Verify the fstab syntax:

```bash
findmnt --verify --verbose
```

> **Warning:** Do not unmount a live MySQL data directory just to test `/etc/fstab`. Only test remounting during a maintenance window, with MySQL stopped and the mount state confirmed.

The `_netdev` option is important because it tells the system that this filesystem depends on networking.

---

## 6.5 Set Ownership and Permissions

This was the command that resolved the ownership issue in the setup:

```bash
chown -R mysql:nfsuser /var/lib/mysql_data
```

Check the result:

```bash
ls -ld /var/lib/mysql_data
ls -la /var/lib/mysql_data
```

The directory should be accessible by the `mysql` user, and files should have ownership similar to:

```text
mysql nfsuser
```

Example expected directory permission:

```text
drwxrws--- mysql nfsuser /var/lib/mysql_data
```

The setgid bit, shown as `s` in the group execute position, is useful because new files and directories inherit the group `nfsuser`.

> **Important:** `chown -R` changes ownership recursively. Use it only after confirming that:
>
> - The correct NFS mount is active.
> - MySQL is stopped.
> - The directory is the intended shared data directory.
> - No other MySQL instance is using the same data.
>
> Do not apply recursive ownership changes blindly to an existing database.

If `chown` fails because of `root_squash`, perform the ownership change on the NFS server against:

```bash
/srv/nfs-dbstorage
```

or use a controlled maintenance procedure.

---

## 6.6 Test Access as the MySQL User

Run these commands on `db-node1`.

List the shared directory as MySQL:

```bash
su -s /bin/bash -c 'ls -la /var/lib/mysql_data' mysql
```

Create a temporary test file:

```bash
su -s /bin/bash -c 'touch /var/lib/mysql_data/nfs_test.txt' mysql
```

Verify the test file:

```bash
ls -l /var/lib/mysql_data/nfs_test.txt
```

Remove the test file:

```bash
su -s /bin/bash -c 'rm /var/lib/mysql_data/nfs_test.txt' mysql
```

All commands should complete without permission errors.

If these commands succeed, the NFS permissions and ownership are working for the MySQL user.

---

## 6.7 Verify MySQL Configuration

Check the MySQL configuration file:

```bash
grep -E '^(datadir|socket|pid-file|log-error)' /etc/my.cnf
```

The data directory should be:

```ini
datadir=/var/lib/mysql_data
```

Example relevant configuration:

```ini
[client]
socket=/var/lib/mysql/mysql.sock

[mysqld]
user=mysql
basedir=/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64
datadir=/var/lib/mysql_data
socket=/var/lib/mysql/mysql.sock
pid-file=/run/mysqld/mysqld.pid
log-error=/var/log/mysql/error.log
```

The socket, PID file, and error log should remain local to the database node. Only the database files should be on NFS.

Verify effective MySQL options:

```bash
/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/bin/my_print_defaults mysqld
```

Confirm that the datadir is correct and that `--initialize` is not present unless intentionally used for a fresh database.

Only start MySQL after confirming:

- NFS is mounted.
- MySQL user can read/write the datadir.
- No other MySQL instance is using the same datadir.
- `/etc/my.cnf` points to the correct datadir.

Check service status:

```bash
systemctl status mysqld --no-pager
```

Start MySQL:

```bash
systemctl start mysqld
```

Check status again:

```bash
systemctl status mysqld --no-pager
```

Check MySQL responsiveness:

```bash
/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/bin/mysqladmin \
  --socket=/var/lib/mysql/mysql.sock -uroot -p ping
```

Expected:

```text
mysqld is alive
```

Verify the actual data directory used by MySQL:

```bash
/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/bin/mysql \
  --socket=/var/lib/mysql/mysql.sock -uroot -p \
  -e "SELECT @@hostname, @@datadir;"
```

Expected datadir:

```text
/var/lib/mysql_data/
```

Check databases:

```bash
/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/bin/mysql \
  --socket=/var/lib/mysql/mysql.sock -uroot -p \

```

Check the error log:


## 7. Explanation of Directory Permission `2770`

The NFS server directory was configured with permissions similar to:

```bash
chmod 2770 /srv/nfs-dbstorage
```

Meaning:

| Digit | Meaning |
|---|---|
| `2` | Setgid bit. New files and directories inherit the parent directory group. |
| `7` | Owner permissions: read, write, execute. |
| `7` | Group permissions: read, write, execute. |
| `0` | Others: no permissions. |

In symbolic form:

```text
drwxrws---
```

This means:

- Owner can access the directory.
- Members of the group can access the directory.
- Everyone else is denied.
- New files/directories inherit the group, which helps maintain consistent access.

However:

> `2770` does not bypass NFS `root_squash`.

Client `root` is still mapped to an unprivileged identity by the NFS server. To give client root full server-root access, you would need `no_root_squash`, but that has security implications and is not required for this setup.

---

## 8. Why Adding Local `root` to `nfsuser` Did Not Solve Everything

Adding root to the local group:

```bash
usermod -aG nfsuser root
```

does not necessarily give root access to the NFS share when `root_squash` is enabled.

Reason:

- NFS evaluates the credentials presented to the server.
- Client `root` is squashed to an unprivileged identity.
- The local group membership of root on the client does not override the server-side mapping.

The correct approach for MySQL is:

- Use the `mysql` service account.
- Ensure `mysql` has the correct supplementary GID.
- Ensure the NFS directory grants access to that GID.
- Ensure file ownership inside the share allows MySQL to read/write.

## 10. Safety Rules

### 10.1 Do Not Run Two MySQL Instances Against the Same Writable Datadir

This is the most important rule.

If a second database node is added later, you must ensure:

1. MySQL is completely stopped on the active node.
2. The stopped node is verified with `systemctl is-active mysqld`.
3. The NFS mount is verified on the target node.
4. MySQL is started only on the target node.

Never rely on guesswork.

### 10.2 Do Not Treat NFS as a Backup

NFS provides shared storage. It does not provide database backup protection.

You still need:

- Logical backups using `mysqldump` or MySQL Shell dump utilities.
- Physical backups if required.
- Backup retention.
- Restore testing.

### 10.3 Do Not Start MySQL Against an Empty Shared Directory Unless Intended

If the shared directory contains only test files and not the intended database files, do not start MySQL against it unless you intentionally want to create or initialize a new database there.

For an existing database, migrate the data safely first.

### 10.4 Be Careful With `chown -R`

Recursive ownership changes can damage a running database if applied incorrectly.

Use `chown -R` only when:

- MySQL is stopped.
- The mount is confirmed.
- The target directory is confirmed.
- No other node is using the data.

## 12. What Was Resolved

The setup was resolved by aligning four things:

1. **NFS export configuration**
   - Correct export path.
   - Correct client IP.
   - Correct options: `rw`, `sync`, `root_squash`, `no_subtree_check`.

2. **Group identity**
   - `nfsuser` exists with GID `1000`.
   - MySQL user belongs to GID `1000`.

3. **Mount configuration**
   - NFS export mounted at `/var/lib/mysql_data`.
   - Mount verified with `findmnt`.
   - Persistent mount added to `/etc/fstab` with `_netdev`.

4. **Ownership and permissions**
   - Shared directory permissions allow group access.
   - Setgid bit helps new files inherit `nfsuser`.
   - Existing files corrected with:

```bash
chown -R mysql:nfsuser /var/lib/mysql_data
```

After these steps, the MySQL user could access the NFS-backed data directory, and MySQL could be configured to use:

```ini
datadir=/var/lib/mysql_data
```
