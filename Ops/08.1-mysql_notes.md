They are beginner-friendly and use the paths observed on your AlmaLinux

## 1. Basic concepts

-   **MySQL Server (`mysqld`)**: background service that manages
    databases and stores data.
-   **MySQL Client (`mysql`)**: command-line program used to connect to
    the server and run SQL.
-   **SQL**: language used to create, read, update, and delete database
    objects and data.
-   **Database**: container for tables and other objects.
-   **Table**: data arranged in rows and columns.
-   **Row**: one record.
-   **Column**: one field in a record.

Example from your lab:

-   Database: `testdb`
-   Table: `employees`
-   Columns: `id`, `name`, `department`
-   Example row: `1, Ahmed, DevOps`

**Linux root and MySQL root are different accounts.** Logging in as
Linux `root` does not automatically mean you are logged in as MySQL
`root`.

## 2. Connect to MySQL

Run this in the Linux terminal:

``` bash
mysql -u root -p
```

-   `mysql`: starts the MySQL client.
-   `-u root`: uses the MySQL account named `root`.
-   `-p`: prompts for its password.

Inside MySQL, the prompt looks like `mysql>`.

Useful commands:

``` sql
SELECT VERSION();
SELECT USER(), CURRENT_USER();
EXIT;
```

`VERSION()` shows the server version. `USER()` shows the supplied login
identity; `CURRENT_USER()` shows the MySQL account MySQL actually
matched.

## 3. Essential SQL commands

Run these inside the MySQL client.

### Databases

``` sql
SHOW DATABASES;
CREATE DATABASE testdb;
USE testdb;
```

-   `SHOW DATABASES` lists databases visible to your account.
-   `CREATE DATABASE` creates a database.
-   `USE` selects the database for your current session.

### Tables

``` sql
SHOW TABLES;
```

Create a table:

``` sql
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    department VARCHAR(100)
);
```

-   `INT`: integer number.
-   `VARCHAR(100)`: text up to 100 characters.
-   `PRIMARY KEY`: uniquely identifies each row.

Insert a row:

``` sql
INSERT INTO employees (id, name, department)
VALUES (1, 'Ahmed', 'DevOps');
```

Read rows:

``` sql
SELECT * FROM employees;
SELECT name, department FROM employees;
```

Filter rows:

``` sql
SELECT * FROM employees WHERE department = 'DevOps';
```

Update a row:

``` sql
UPDATE employees
SET department = 'Cloud'
WHERE id = 1;
```

Delete a row:

``` sql
DELETE FROM employees WHERE id = 1;
```

**Caution:** An `UPDATE` or `DELETE` without `WHERE` can affect every
row in the table.

Inspect table structure:

``` sql
DESCRIBE employees;
SHOW CREATE TABLE employees;
```

Remove objects (destructive):

``` sql
DROP TABLE employees;
DROP DATABASE testdb;
```

`DROP` removes the table or database. Do not use it unless you intend to
remove that object.

## 4. MySQL users and permissions

A MySQL account is identified by both a username and a host:

``` text
'username'@'host'
```

For example, `'testuser'@'localhost'` is not necessarily the same
account as `'testuser'@'%'`.

-   `localhost`: account intended for local connections.
-   `%`: wildcard host matching many remote host names/IPs. It does not
    bypass network or firewall restrictions.

Create a lab user:

``` sql
CREATE USER 'testuser'@'localhost'
IDENTIFIED BY 'use-a-strong-password';
```

Grant access to one database:

``` sql
GRANT ALL PRIVILEGES ON testdb.*
TO 'testuser'@'localhost';
```

Show grants:

``` sql
SHOW GRANTS FOR 'testuser'@'localhost';
```

Your lab output was similar to:

``` sql
GRANT USAGE ON *.* TO `testuser`@`localhost`
GRANT ALL PRIVILEGES ON `testdb`.* TO `testuser`@`localhost`
```

Meaning:

  Expression         Meaning
  ------------------ -------------------------------------------------------
  `USAGE`            Account exists; this grant itself gives no privileges
  `*.*`              Global scope: all databases and tables
  `testdb.*`         All tables in the `testdb` database
  `ALL PRIVILEGES`   All privileges available at that scope

The `USAGE` line does not cancel the database-level grant. The second
line gives privileges on `testdb`.

List accounts:

``` sql
SELECT User, Host FROM mysql.user;
```

Find one account:

``` sql
SELECT User, Host
FROM mysql.user
WHERE User = 'testuser';
```

Revoke the database grant:

``` sql
REVOKE ALL PRIVILEGES ON testdb.*
FROM 'testuser'@'localhost';
```

Remove the account:

``` sql
DROP USER 'testuser'@'localhost';
```

Dropping a user does not drop the database. Password `123` used in an
earlier lab example is weak and should never be used on a real server.

## 6. Understanding your table's `.ibd` file

You created `testdb.employees` and found:

``` text
/var/lib/mysql_data/testdb/employees.ibd
```

An `.ibd` file is an InnoDB tablespace file. With file-per-table
storage, it contains that table's data and indexes.

You saw a size of about `112K`. This includes InnoDB pages, indexes, and
storage overhead. It is not simply the size of the text in the rows.

An `.ibd` file is binary, not a normal text file. `cat` and ordinary
`grep` cannot reliably display its records. Do not edit or delete it
manually.

## 7. Where MySQL account information is stored

In MySQL 8.0, `mysql.user` is a view for displaying account information.
The underlying account data is stored in the `mysql.global_priv` system
table.

In your setup, this file existed:

``` text
/var/lib/mysql_data/mysql.ibd
```

You inspected `/var/lib/mysql_data/mysql/` and saw:

``` text
general_log.CSM
general_log.CSV
general_log_213.sdi
slow_log.CSM
slow_log.CSV
slow_log_214.sdi
```

Those files are related to log tables. They are not a list of MySQL
users. The system tablespace is not necessarily represented by a file
named `user.ibd`.

### Your filesystem experiment with `strings`

You installed the utility on AlmaLinux:

``` bash
dnf install -y binutils
```

Then searched the tablespace:

``` bash
strings /var/lib/mysql_data/mysql.ibd | grep -i testuser
```

You found readable fragments including `testuser`, `localhost`,
`testdb`, and `Definer: testuser@localhost`.

What the command does:

-   `strings`: extracts printable text fragments from a binary file.
-   `|`: passes the first command's output to the next command.
-   `grep -i testuser`: finds lines containing `testuser`, ignoring
    letter case.

**Important:** This is an experiment, not a reliable way to list
accounts. InnoDB stores data in binary pages. `strings` does not decode
full records or prove which table each fragment belongs to. No match
does not mean the account is absent.

Use SQL for authoritative account information:

``` sql
SELECT User, Host
FROM mysql.user
WHERE User = 'testuser';
```

You can also inspect the underlying table:

``` sql
SELECT User, Host
FROM mysql.global_priv
WHERE User = 'testuser';
```

## 8. MySQL logs: what they do

Logs help administrators troubleshoot errors, investigate slow queries,
understand connections, and support replication or recovery. Not all
logs are enabled by default.

### A. Error log

**Purpose:** Records server errors, warnings, startup/shutdown messages,
and certain operational problems.

Useful when MySQL will not start or reports storage/configuration
problems.

Find the configured path:

``` sql
SHOW VARIABLES LIKE 'log_error';
```

On AlmaLinux, service messages can also be inspected with:

``` bash
journalctl -u mysqld
journalctl -u mysqld -n 50
journalctl -u mysqld -f
```

`-n 50` shows the latest 50 lines; `-f` follows new messages.

### B. General query log

**Purpose:** Records client connections and SQL statements received by
the server.

It can help answer: who connected, and what SQL statements were sent?

Check settings:

``` sql
SHOW VARIABLES LIKE 'general_log';
SHOW VARIABLES LIKE 'general_log_file';
SHOW VARIABLES LIKE 'log_output';
```

The general log can grow quickly and add overhead. It is usually enabled
temporarily for troubleshooting, rather than left on continuously on
busy production servers.

### C. Slow query log

**Purpose:** Records SQL statements that take longer than a configured
time threshold. It helps identify queries that may need optimization.

Check settings:

``` sql
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'slow_query_log_file';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
SHOW VARIABLES LIKE 'log_output';
```

Important settings:

  -----------------------------------------------------------------------
  Setting                             Meaning
  ----------------------------------- -----------------------------------
  `slow_query_log`                    Enables/disables the slow query log

  `slow_query_log_file`               File path used for the slow log

  `long_query_time`                   Time threshold, in seconds

  `log_queries_not_using_indexes`     Can log queries that do not use
                                      indexes

  `log_output`                        Destination: `FILE`, `TABLE`, or
                                      both
  -----------------------------------------------------------------------

Example: set a 2-second threshold and enable the slow log at runtime:

``` sql
SET GLOBAL long_query_time = 2;
SET GLOBAL slow_query_log = ON;
```

These runtime settings may not persist after a restart unless configured
in the MySQL configuration file. You need suitable privileges to change
global settings.

A slow query can consume CPU, memory, disk I/O, and database
connections. The slow log helps identify queries worth investigating.

### D. Binary log (binlog)

**Purpose:** Records database changes in a format used for replication
and point-in-time recovery.

Common uses:

-   Replication between MySQL servers.
-   Recovering data to a particular point in time when used with a
    suitable backup.
-   Tracking database changes.

You saw files like:

``` text
binlog.000001
binlog.000002
binlog.000003
binlog.index
```

Check binary logging:

``` sql
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'log_bin_basename';
SHOW BINARY LOGS;
```

Inspect a binary log from Linux:

``` bash
mysqlbinlog /var/lib/mysql_data/binlog.000001
```

Use the real file path from your server. Binlogs are not the same as
general/slow logs: they are mainly for changes, replication, and
recovery, not a record of every `SELECT`.

### E. Relay log

**Purpose:** Used by a replica in MySQL replication. It stores events
received from the source before the replica applies them. You may not
see relay logs on a standalone server.

### F. Audit log

**Purpose:** Records security-related activity, such as connections and
selected SQL events, depending on the audit plugin or service.

It can support security investigations and compliance. Availability
depends on the MySQL edition, plugins, and deployment.

### Quick comparison

  Log                 Main purpose
  ------------------- -------------------------------------------
  Error log           Errors, warnings, startup/shutdown
  General query log   Connections and SQL statements received
  Slow query log      Queries taking longer than a threshold
  Binary log          Database changes for replication/recovery
  Relay log           Events received by a replica
  Audit log           Security and audit events

## 9. Why were your CSV log files empty?

You saw:

``` text
general_log.CSV    0 bytes
slow_log.CSV       0 bytes
```

`0 bytes` means the files contained no data at the time you checked.

These are log-table files, not the files where your `employees` table
records are stored. Your employee table was in:

``` text
/var/lib/mysql_data/testdb/employees.ibd
```

The general/slow logs may have been disabled, may have been writing to a
file instead of a table, or may not have recorded events.

Check:

``` sql
SHOW VARIABLES LIKE 'general_log';
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'log_output';
SHOW VARIABLES LIKE 'general_log_file';
SHOW VARIABLES LIKE 'slow_query_log_file';
```

`log_output` controls whether general and slow logs write to `FILE`,
`TABLE`, or both. `general_log` and `slow_query_log` control whether
those logs are enabled.

## 11. Useful Linux commands for MySQL administrators

Run these in the Linux terminal, not at the `mysql>` prompt.

### Service status and control

``` bash
systemctl status mysqld
systemctl start mysqld
systemctl stop mysqld
systemctl restart mysqld
systemctl enable mysqld
```

-   `status`: checks service status.
-   `start` / `stop`: starts or stops MySQL.
-   `restart`: restarts MySQL. Be careful if applications are using it.
-   `enable`: configures the service to start at boot.

### Process, disk, and files

``` bash
ps -ef | grep '[m]ysqld'
du -sh /var/lib/mysql_data
ls -lah /var/lib/mysql_data
find /var/lib/mysql_data -name '*.ibd'
find /var/lib/mysql_data -maxdepth 1 -type f -ls
```

-   `ps`: displays running processes.
-   `du -sh`: displays total directory size in a readable format.
-   `ls -lah`: lists files, including hidden files, with readable sizes.
-   `find`: searches for files.

### Read text logs

``` bash
less /path/to/mysql-error.log
tail -f /path/to/mysql-error.log
```

Replace the example path with the actual log path. `tail -f` follows new
log lines as they are written.

### Check file ownership

``` bash
ls -l /var/lib/mysql_data
```

MySQL data files are normally owned by the Linux `mysql` user and group.
Do not change ownership or permissions casually.

## 12. MySQL file types: quick reference

  -----------------------------------------------------------------------
  File/directory                      General purpose
  ----------------------------------- -----------------------------------
  `.ibd`                              InnoDB tablespace; may contain
                                      table data and indexes

  `ibdata1`                           InnoDB system tablespace

  `undo_*`                            Undo data used for rollback and
                                      multi-version concurrency control

  `#innodb_redo`                      InnoDB redo log files

  `#innodb_temp`                      InnoDB temporary tablespace

  `binlog.*`                          Binary log files

  `binlog.index`                      List/index of binary log files

  `.CSV`                              Data file for a CSV table

  `.CSM`                              CSV storage-engine metadata

  `.sdi`                              Serialized dictionary information
                                      (table metadata)

  `.pem`                              Certificate or key file, depending
                                      on its name and role

  `auto.cnf`                          MySQL server identity/configuration
                                      information
  -----------------------------------------------------------------------

Do not manually edit, delete, or move MySQL data files while the server
is running. This can corrupt data or prevent MySQL from starting.

## 13. Safety rules to remember

1.  Use SQL to manage databases, tables, and users. Do not edit `.ibd`
    files manually.
2.  Linux accounts and MySQL accounts are separate.
3.  Check `datadir` before searching for database files.
4.  Check log settings before assuming a log is enabled or stored in a
    particular location.
5.  Do not delete binary logs casually. They may be needed for
    replication or point-in-time recovery.
6.  Never share private keys such as `server-key.pem`, `client-key.pem`,
    or `ca-key.pem`.
7.  Use strong passwords. Do not use simple lab passwords on real
    servers.
8.  Back up before making important changes, and test that backups can
    be restored.
9.  Be careful with destructive SQL such as `DROP`, `DELETE`, and
    `UPDATE`.
10. Treat `strings` as a learning experiment, not as a supported way to
    inspect MySQL records.
