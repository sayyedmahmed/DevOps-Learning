# High Availability: MaxScale with Keepalived (VIP)

**Architecture:** Keepalived floats a Virtual IP (VIP) between two MaxScale nodes. The application connects only to the VIP. If the primary MaxScale dies, Keepalived instantly moves the VIP to the backup MaxScale, keeping the app online.

```text
                  ┌─────────────────────────────┐
                  │   App VM (10.10.10.180)     │
                  │   config.php db_host = VIP  │
                  └──────────────┬──────────────┘
                                 │
                   Connects to   │  10.10.10.250:4006 (VIP)
                                 │
                  ┌──────────────▼──────────────┐
                  │       Keepalived VIP        │
                  └──────┬───────────────┬──────┘
                         │               │
            (Active)     │               │     (Standby)
    ┌────────────────────▼───┐       ┌───▼────────────────────┐
    │ MaxScale 1             │       │ MaxScale 2             │
    │ 10.10.10.190           │       │ 10.10.10.191           │
    │ Holds VIP (MASTER)     │       │ No VIP (BACKUP)        │
    └────────────┬───────────┘       └───────────┬────────────┘
                 │                               │
                 └──────────────┬────────────────┘
                                │ Port 3306
                  ┌─────────────▼─────────────┐
                  │    MariaDB Galera Cluster │
                  │ 10.10.10.201 / 202 / 203  │
                  └───────────────────────────┘
```

## 1. Critical Prerequisites (Do this first)

### 1.1 Fix `rp_filter` (Multi-NIC SSH Lockout Prevention)
In this lab, `eth0` is internet and `eth1` is internal. Linux Reverse Path Filtering will drop packets and lock you out of SSH if the VIP moves. **Run on both MaxScale nodes:**
```bash
echo 'net.ipv4.conf.all.rp_filter = 2' | sudo tee /etc/sysctl.d/99-rpfilter.conf
echo 'net.ipv4.conf.eth0.rp_filter = 2' | sudo tee -a /etc/sysctl.d/99-rpfilter.conf
echo 'net.ipv4.conf.eth1.rp_filter = 2' | sudo tee -a /etc/sysctl.d/99-rpfilter.conf
sudo sysctl --system
```

### 1.2 Database Users (Run on Galera Node `.201`)
MaxScale and the App need specific users on the database. Notice the host pattern `10.10.10.%` (because the DB sees MaxScale's IP, not the App's).
```sql
-- MaxScale Monitor & Service User
CREATE USER 'max'@'10.10.10.%' IDENTIFIED BY '123';
GRANT REPLICATION CLIENT, REPLICATION SLAVE, SELECT ON *.* TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.procs_priv TO 'max'@'10.10.10.%';

-- Application User
CREATE USER 'appuser'@'10.10.10.%' IDENTIFIED BY '123';
GRANT SELECT, INSERT, UPDATE, DELETE ON app_data.* TO 'appuser'@'10.10.10.%';
FLUSH PRIVILEGES;
```

## 2. MaxScale Configuration (`/etc/maxscale.cnf`)

**Run on both MaxScale nodes (`.190` and `.191`):**
```ini
[maxscale]
threads=auto

[mariadb-1]
type=server
address=10.10.10.201
port=3306

[mariadb-2]
type=server
address=10.10.10.202
port=3306

[mariadb-3]
type=server
address=10.10.10.203
port=3306

[Galera-Monitor]
type=monitor
module=galeramon
servers=mariadb-1,mariadb-2,mariadb-3
user=max
password="123"
monitor_interval=2000ms

[Read-Write-Service]
type=service
router=readwritesplit
servers=mariadb-1,mariadb-2,mariadb-3
user=max
password="123"

# CRITICAL: Listen on 0.0.0.0 so MaxScale starts even before Keepalived adds the VIP
[Read-Write-Listener]
type=listener
service=Read-Write-Service
protocol=MariaDBClient
address=0.0.0.0
port=4006
```

## 3. Keepalived Configuration

### 3.1 Primary Node (`maxscale-1` — 10.10.10.190)
File: `/etc/keepalived/keepalived.conf`
```conf
global_defs {
    router_id MAXSCALE_1
    enable_script_security
    script_user root
}

vrrp_script chk_maxscale {
    script "/usr/bin/ss -tln | /usr/bin/grep -q ':4006 '"
    interval 2
    weight -30
    fall 3
    rise 2
}

vrrp_instance VI_MAXSCALE {
    state MASTER
    interface eth1                 # MUST BE eth1
    virtual_router_id 51           # Same on both
    priority 150                   # Higher = MASTER
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass ChangeMe123      # Same on both
    }
    virtual_ipaddress {
        10.10.10.250/24 dev eth1   # MUST BE eth1
    }
    track_script {
        chk_maxscale
    }
}
```

### 3.2 Backup Node (`maxscale-2` — 10.10.10.191)
File: `/etc/keepalived/keepalived.conf`
```conf
global_defs {
    router_id MAXSCALE_2
    enable_script_security
    script_user root
}

vrrp_script chk_maxscale {
    script "/usr/bin/ss -tln | /usr/bin/grep -q ':4006 '"
    interval 2
    weight -30
    fall 3
    rise 2
}

vrrp_instance VI_MAXSCALE {
    state BACKUP
    interface eth1                 # MUST BE eth1
    virtual_router_id 51           # Same on both
    priority 100                   # Lower = BACKUP
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass ChangeMe123      # Same on both
    }
    virtual_ipaddress {
        10.10.10.250/24 dev eth1   # MUST BE eth1
    }
    track_script {
        chk_maxscale
    }
}
```

## 4. Firewall Configuration

**Run on both MaxScale nodes:**
```bash
# Allow VRRP (Keepalived communication)
sudo firewall-cmd --permanent --add-rich-rule='rule protocol value="112" accept'

# Allow App VM to reach the VIP on MaxScale port
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="10.10.10.180" destination address="10.10.10.250" port port="4006" protocol="tcp" accept'

sudo firewall-cmd --reload
```

## 5. Start Services & Validate

1. **Start MaxScale:**
   ```bash
   sudo systemctl enable --now maxscale
   ```
2. **Start Keepalived:**
   ```bash
   sudo systemctl enable --now keepalived
   ```
3. **Verify VIP Location:**
   ```bash
   ip -br a | grep 10.10.10.250
   # Expected: eth1 UP 10.10.10.190/24 10.10.10.250/24
   ```
4. **Verify MaxScale Logs (Success State):**
   ```bash
   sudo tail -n 30 /var/log/maxscale/maxscale.log
   ```
   *You should see: `Listening for connections at [10.10.10.250]:4006` and no warnings.*

## 7. Troubleshooting: The Issues We Actually Faced

During this build, we hit 7 specific roadblocks. If you reproduce this, here is exactly what went wrong and how to fix it.

### Issue 1: `ERROR 2002 (115)` - Can't connect to server via VIP
*   **Cause:** The App VM couldn't reach the VIP on port 4006.
*   **Diagnosis:** Run `traceroute -n -T -p 4006 10.10.10.250`. If it returns 1 hop successfully, the network route is fine. The issue is a **Firewall** on MaxScale blocking the port.
*   **Fix:** Add the `firewall-cmd --add-rich-rule` (See Section 4). Ensure `destination address="10.10.10.250"` is explicitly stated.

### Issue 2: SSH Lockout (Xshell "Connection failed")
*   **Cause:** We accidentally put the VIP on `dev eth0` (the internet NIC) instead of `dev eth1` (the internal NIC). This confused the Linux routing table, and SSH replies went out the wrong door. Furthermore, `rp_filter` dropped the incoming SSH packets.
*   **Fix:** 
    1. Log into the VM console (Proxmox/VMware).
    2. Stop keepalived: `systemctl stop keepalived`.
    3. Delete the VIP from the wrong card: `ip addr del 10.10.10.250/24 dev eth0`.
    4. Change `dev eth0` to `dev eth1` in `keepalived.conf`.
    5. Apply the `rp_filter=2` fix (See Section 1.1).

### Issue 3: `Unknown column 'user' in 'SELECT'`
*   **Cause:** MariaDB column names are case-sensitive. 
*   **Fix:** Use `SELECT User, Host FROM mysql.user;` (capital `U`).

### Issue 4: MaxScale Warning: "Using old user account query due to insufficient privileges"
*   **Cause:** The `max` user could monitor the cluster, but couldn't read the `mysql.procs_priv` table, forcing MaxScale to use an outdated fallback method to check permissions.
*   **Fix:** On a Galera node: `GRANT SELECT ON mysql.procs_priv TO 'max'@'10.10.10.%'; FLUSH PRIVILEGES;`

### Issue 5: `Failed to bind to 10.10.10.250` (MaxScale Crash)
*   **Cause:** MaxScale tried to start on boot, but Keepalived hadn't assigned the VIP to the server yet.
*   **Fix:** Set `address=0.0.0.0` in the `[Read-Write-Listener]` block. MaxScale listens on all IPs, and Keepalived assigns the VIP later.

### Issue 6: App VM `SQLSTATE[HY000] [2002] Connection refused`
*   **Cause:** The App config was pointing to the old single-VM DB port (`3306`) instead of the MaxScale listener port (`4006`).
*   **Fix:** Change `db_port` to `4006` in `config.php`.

### Issue 7: App VM `Access denied for user 'appuser'@'10.10.10.190'`
*   **Cause:** The user was created as `'appuser'@'10.10.10.180'`. Because MaxScale is a proxy, the database sees the connection coming from MaxScale's IP (`.190`), not the App VM's IP (`.180`).
*   **Fix:** Create the user as `'appuser'@'10.10.10.%'` on the Galera node.
