Always cross-reference the [Official MariaDB Documentation](https://mariadb.com/docs) for the specific version deployed in your environment.

## 1. Architecture Overview and Core Components

### 1.1 MariaDB MaxScale Proxy
MariaDB MaxScale functions as an enterprise-grade database proxy middleware. It intercepts application traffic, abstracting the underlying database topology from client applications. Applications communicate with MaxScale using standard MySQL/MariaDB protocols, while MaxScale dynamically routes queries to the appropriate backend database instances based on query type, server health, and configured routing logic.

```text
  WITHOUT MaxScale                       WITH MaxScale
  App ------------> DB server            App ---> MaxScale ---+--> DB 1 (Primary)
                                                              |
                                                              +--> DB 2 (Replica)
```

### 1.2 Architectural Challenges Addressed

| Challenge | Architectural Solution |
| :--- | :--- |
| **Read Scalability** | Distributes read-heavy workloads across multiple replicas while directing write operations exclusively to the primary node. |
| **Topology Abstraction** | Applications connect to a single virtual IP/Port. Backend servers can be added, removed, or maintained without modifying application connection strings. |
| **High Availability** | Automatically detects primary node failures and promotes a replica (Failover), or facilitates planned maintenance (Switchover) with zero application reconfiguration. |
| **Connection Management** | Pools and multiplexes connections, preventing backend database exhaustion during application traffic spikes. |

## 2. MaxScale Core Architecture

### 2.1 The Five Building Blocks
MaxScale configuration is object-oriented, relying on five core components:

```text
  CLIENT
    |
    v
 +----------+      +-----------+      +----------+      +----------+
 | LISTENER | ---> |  SERVICE  | ---> |  SERVER  | <--- | MONITOR  |
 +----------+      +-----------+      +----------+      +----------+
```

| Object | Definition | Enterprise Function |
| :--- | :--- | :--- |
| **Server** | Defines a physical backend database instance (IP and Port). | Represents the actual data nodes. |
| **Monitor** | A daemon that continuously polls server health and replication state. | Detects failures and triggers topology changes. |
| **Router** | The logic engine that evaluates and directs incoming queries. | Executes Read/Write splitting or connection routing. |
| **Service** | Binds a Router to a specific set of Servers and Monitors. | Defines the logical proxy endpoint. |
| **Listener** | The network port and protocol exposed to client applications. | The ingress point for database traffic. |
| **Filter** | (Optional) Intercepts queries for logging, rewriting, or caching. | Provides auditing and security enforcement. |

### 2.2 Routing Modules

| Router Module | Behavior | Use Case |
| :--- | :--- | :--- |
| `readwritesplit` | Analyzes SQL statements. Writes/Transactions route to Primary; Reads route to Replicas. | Standard OLTP applications requiring read scalability. |
| `readconnroute` | Assigns a backend server upon connection establishment. The session remains pinned. | Simple load balancing, read-only analytics pools, or single-node deployments. |

## 3. Licensing, Compatibility, and Ecosystem

### 3.1 Business Source License (BSL)
MaxScale 2.x and later operate under the Business Source License (BSL).
*   **Testing/Development**: Free.
*   **Production**: Free for a limited number of backend servers (typically up to two). Exceeding this limit requires a commercial MariaDB subscription.
*   **GPL Conversion**: Each version automatically converts to the GPL license after its designated "Change Date".
*   *Reference*: Consult the `LICENSE.TXT` and the [Official MariaDB Documentation](https://mariadb.com/docs) for exact terms applicable to your deployed version.

### 3.2 Backend Database Compatibility
*   **MariaDB**: Fully supported. Required for advanced features like `causal_reads` and GTID-based automated failover.
*   **MySQL**: Basic routing functions may operate, but MariaDB-specific extensions are unsupported. MySQL 8's default `caching_sha2_password` authentication is not directly supported; backend accounts must utilize `mysql_native_password`.

### 3.3 Alternative Proxy Solutions
*   **ProxySQL**: Open-source (GPL) proxy with deep query routing and caching capabilities.
*   **MySQL Router**: Oracle's native router, optimized for MySQL InnoDB Cluster.
*   **HAProxy**: Layer 4 TCP load balancer (lacks SQL-aware Read/Write splitting).

## 4. Infrastructure Implementation Sequence

### 4.1 Network Topology and Node Provisioning
The following implementation utilizes a standard enterprise subnet schema. Replace IP addresses with your environment's specific network design.

| Node Role | IP Address | Function |
| :--- | :--- | :--- |
| **DB1 (Primary)** | `10.10.10.201` | Accepts Write operations, sources replication. |
| **DB2 (Replica)** | `10.10.10.202` | Read-only, maintains asynchronous/GTID replication. |
| **MaxScale Proxy** | `10.10.10.203` | Middleware proxy, exposes port `4006`. |

### 4.2 MariaDB Backend Deployment

#### 4.2.1 Single Node Deep Configuration and InnoDB Architecture
When deploying a Single Node MariaDB instance, or establishing the foundational node for a replicated cluster, deep understanding of the InnoDB storage engine is critical for enterprise performance and data integrity.

*   **InnoDB Buffer Pool**: The primary memory area where InnoDB caches table and index data. For a dedicated single-node database server, `innodb_buffer_pool_size` should be configured to 70-80% of total system RAM. This minimizes disk I/O by keeping the working set in memory.
*   **Redo Logs (Write-Ahead Logging)**: Ensures ACID compliance and crash recovery. Changes are written to the redo log buffer and flushed to disk. Tuning `innodb_log_file_size` and `innodb_log_files_in_group` balances crash recovery time against write performance.
*   **Undo Logs and MVCC**: Multi-Version Concurrency Control (MVCC) relies on undo logs to provide consistent reads without locking. Proper sizing of the undo tablespace prevents transaction stalls during long-running queries.
*   **Doublewrite Buffer**: A storage area where InnoDB writes pages before writing them to the actual data files. This protects against partial page writes and data corruption in the event of an OS crash or power failure.
*   **Binary Logging and GTID**: Even on a single node, `log_bin` and `binlog_format=ROW` must be enabled for Point-in-Time Recovery (PITR) and to prepare the node for future replication or MaxScale monitoring. Global Transaction IDs (GTID) provide a robust mechanism for tracking transaction execution across topologies.

**Base Installation (RHEL/AlmaLinux/Rocky):**
```bash
sudo dnf install mariadb-server -y
sudo systemctl enable --now mariadb
sudo mysql_secure_installation
```

**Core Configuration (`/etc/my.cnf.d/mariadb-server.cnf`):**
```ini
[mysqld]
bind-address      = 0.0.0.0
server_id         = 1
log_bin           = mariadb-bin
log_slave_updates = ON
binlog_format     = ROW
# Deep InnoDB Tuning
innodb_buffer_pool_size = 4G  # Adjust to 70-80% of RAM
innodb_log_file_size    = 512M
innodb_flush_log_at_trx_commit = 1
innodb_flush_method     = O_DIRECT
```

#### 4.2.2 Primary/Replica Topology Configuration
To enable Read/Write splitting, a secondary replica node must be provisioned.

**Replica Configuration (`/etc/my.cnf.d/mariadb-server.cnf` on DB2):**
```ini
[mysqld]
bind-address      = 0.0.0.0
server_id         = 2
log_bin           = mariadb-bin
log_slave_updates = ON
binlog_format     = ROW
read_only         = ON
```

**Firewall Configuration (Both Nodes):**
```bash
sudo firewall-cmd --permanent --add-port=3306/tcp
sudo firewall-cmd --reload
```

**Replication Initialization:**
Execute on Primary (DB1):
```sql
CREATE USER 'repl'@'10.10.10.%' IDENTIFIED BY 'ReplPass#123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.10.10.%';
```

Execute on Replica (DB2):
```sql
CHANGE MASTER TO
  MASTER_HOST='10.10.10.201',
  MASTER_USER='repl',
  MASTER_PASSWORD='ReplPass#123',
  MASTER_USE_GTID=slave_pos;
START SLAVE;
SHOW SLAVE STATUS\G
```
*Verification*: Ensure `Slave_IO_Running: Yes` and `Slave_SQL_Running: Yes`.

### 4.3 Identity and Access Management for Proxy Services
MaxScale requires dedicated service accounts to monitor health and authenticate clients. Execute on the Primary node; replication will propagate these accounts to the Replica.

```sql
-- 1. Monitor Account (Health checks and replication management)
CREATE USER 'maxmon'@'10.10.10.%' IDENTIFIED BY 'MonPass#123';
GRANT SUPER, RELOAD, PROCESS, SHOW DATABASES, EVENT ON *.* TO 'maxmon'@'10.10.10.%';
GRANT REPLICATION CLIENT, REPLICATION SLAVE ON *.* TO 'maxmon'@'10.10.10.%';
GRANT REPLICATION SLAVE ADMIN, READ_ONLY ADMIN ON *.* TO 'maxmon'@'10.10.10.%';

-- 2. Service Account (User authentication synchronization)
CREATE USER 'maxsvc'@'10.10.10.%' IDENTIFIED BY 'SvcPass#123';
GRANT SELECT ON mysql.user         TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.db           TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.tables_priv  TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.columns_priv TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.proxies_priv TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.roles_mapping TO 'maxsvc'@'10.10.10.%';
GRANT SHOW DATABASES ON *.* TO 'maxsvc'@'10.10.10.%';

-- 3. Application Account
CREATE USER 'appuser'@'%' IDENTIFIED BY 'AppPass#123';
GRANT ALL PRIVILEGES ON labtest.* TO 'appuser'@'%';
```
*Note*: Backend servers will see connections originating from the MaxScale IP (`10.10.10.203`). Ensure host patterns (`%` or `10.10.10.%`) accommodate the proxy's IP address.

### 4.5 MaxScale Configuration Management
Backup the default configuration and define the enterprise topology.

```bash
sudo cp /etc/maxscale.cnf /etc/maxscale.cnf.original
sudo vim /etc/maxscale.cnf
```

**Baseline Configuration (`/etc/maxscale.cnf`):**
```ini
[maxscale]
threads=auto

[db1]
type=server
address=10.10.10.201
port=3306

[db2]
type=server
address=10.10.10.202
port=3306

[MariaDB-Monitor]
type=monitor
module=mariadbmon
servers=db1,db2
user=maxmon
password=MonPass#123
monitor_interval=2s

[Read-Write-Service]
type=service
router=readwritesplit
cluster=MariaDB-Monitor
user=maxsvc
password=SvcPass#123
# Single Node Topology Note: If using a single backend node without replicas, 
# add `master_accept_reads=true` to route all traffic to the primary.

[Read-Write-Listener]
type=listener
service=Read-Write-Service
protocol=MariaDBClient
port=4006
```

**Password Encryption (Security Hardening):**
```bash
sudo maxkeys
sudo maxpasswd 'MonPass#123'
sudo maxpasswd 'SvcPass#123'
# Replace plain-text passwords in maxscale.cnf with the generated hashes.
sudo chmod 600 /etc/maxscale.cnf
sudo chown maxscale:maxscale /etc/maxscale.cnf
```

**Syntax Validation:**
```bash

```

## 5. Dynamic Configuration and Runtime Management

MaxScale supports dynamic reconfiguration via the `maxctrl` utility without requiring service restarts.

### 5.1 State Inspection and Maintenance Mode
```bash
maxctrl list servers
maxctrl list services
maxctrl set server db2 maintenance   # Drains connections and removes from rotation
maxctrl clear server db2 maintenance # Restores node to active pool
```

### 5.2 Dynamic Topology Modifications
```bash
maxctrl create server db3 10.10.10.204 3306
maxctrl link monitor MariaDB-Monitor db3
maxctrl link service Read-Write-Service db3
```

### 5.3 Runtime Parameter Adjustments
Runtime changes are persisted in `/var/lib/maxscale/maxscale.cnf.d/` and override static configurations in `/etc/maxscale.cnf`.
```bash
maxctrl alter service Read-Write-Service max_slave_replication_lag=10s
maxctrl alter monitor MariaDB-Monitor monitor_interval=1s
```

## 6. High Availability, Failover, and Switchover Procedures

### 6.1 Planned Switchover Execution
Promotes a replica to primary safely, ensuring zero data loss.
```bash
maxctrl call command mariadbmon switchover MariaDB-Monitor db2 db1
```

### 6.2 Automated Failover and Rejoin Configuration
Enable automatic topology recovery by updating the monitor parameters:
```bash
maxctrl alter monitor MariaDB-Monitor auto_failover=true auto_rejoin=true failcount=5 \
        replication_user=repl replication_password=ReplPass#123
```
*   **`auto_failover=true`**: Promotes a replica if the primary fails.
*   **`auto_rejoin=true`**: Automatically configures the recovered primary as a replica of the new primary.
*   **`failcount=5`**: Requires 5 consecutive failed health checks before declaring a node dead.

### 6.3 Application Resilience and Transaction Replay
Configure the service to handle transient network errors during failover events:
```ini
[Read-Write-Service]
transaction_replay=true
transaction_replay_max_size=1Mi
master_reconnection=true
delayed_retry=true
delayed_retry_timeout=10s
```

## 7. Advanced Routing Parameters and Replication Lag Mitigation

Apply these parameters to the `[Read-Write-Service]` section to optimize traffic distribution and data consistency.

| Parameter | Function |
| :--- | :--- |
| `max_slave_replication_lag=10s` | Excludes replicas lagging >10 seconds behind the primary from the read pool. |
| `slave_selection_criteria=LEAST_CURRENT_OPERATIONS` | Routes reads to the replica with the fewest active operations. |
| `master_accept_reads=true` | Allows the primary to serve read queries (essential for single-node topologies or when replicas are overloaded). |
| `causal_reads=local` | Ensures read-after-write consistency by waiting for the replica to apply the client's previous writes. |
| `master_failure_mode=fail_on_write` | Permits read operations to continue on replicas even if the primary is unavailable. |

## 8. Query Filtering and Auditing

Filters intercept traffic for logging, masking, or rewriting. The Query Log All (QLA) filter is critical for enterprise auditing.

```ini
[QLA]
type=filter
module=qlafilter
filebase=/var/log/maxscale/qla
log_type=unified

[Read-Write-Service]
# ... existing service config ...
filters=QLA
```
*Note*: Filters introduce CPU overhead. Enable only when required for compliance or debugging.

## 9. Cross-Platform Compatibility: MariaDB vs. MySQL

| Feature | MariaDB Backend | MySQL Backend |
| :--- | :--- | :--- |
| **Official Support** | Fully Supported | Basic Routing Only |
| **Automated Failover** | Supported (via MariaDB GTID) | Unsupported / Unreliable |
| **Causal Reads** | Supported | Unsupported |
| **Authentication** | Native / Ed25519 | Requires `mysql_native_password` (MySQL 8+ `caching_sha2_password` is incompatible) |

*Recommendation*: Utilize MariaDB for backend nodes to leverage the full MaxScale feature set. For MySQL environments, evaluate ProxySQL or MySQL Router.

## 10. Edge Load Balancing and Reverse Proxy Integration

In enterprise architectures, MaxScale is often placed behind Layer 4 Load Balancers for high availability, or fronted by Reverse Proxies for application tier integration.

### 10.1 HAProxy TCP Load Balancing
HAProxy is the enterprise standard for raw TCP load balancing of database traffic.

```haproxy
global
    log /dev/log local0
    maxconn 4096
    daemon

defaults
    log     global
    mode    tcp
    option  tcplog
    timeout connect 5000ms
    timeout client  50000ms
    timeout server  50000ms

frontend maxscale_frontend
    bind *:3306
    default_backend maxscale_backend

backend maxscale_backend
    balance roundrobin
    option tcp-check
    server maxscale-node-1 10.10.10.203:4006 check inter 5s fall 3 rise 2
```

### 10.2 Nginx Stream Proxying
Nginx utilizes the `stream` module for high-performance TCP/UDP proxying.

```nginx
stream {
    upstream maxscale_backend {
        server 10.10.10.203:4006;
    }

    server {
        listen 3306;
        proxy_pass maxscale_backend;
        proxy_timeout 1h;
        proxy_connect_timeout 10s;
    }
}
```

### 10.3 Apache HTTP Server Integration
*Note: Apache HTTP Server is primarily designed for HTTP/HTTPS reverse proxying. For raw TCP MySQL protocol proxying, HAProxy or Nginx are recommended. The configuration below demonstrates the application-tier reverse proxy integration (e.g., routing web traffic to the application servers that subsequently query MaxScale).*

```apache
<VirtualHost *:80>
    ServerName db-api.enterprise.local
    ProxyPreserveHost On
    ProxyPass / http://10.10.10.50:8080/
    ProxyPassReverse / http://10.10.10.50:8080/
    
    # Security Headers
    Header always set Strict-Transport-Security "max-age=63072000; includeSubDomains"
    Header always set X-Frame-Options "DENY"
</VirtualHost>
```

## 11. Production Hardening and Security Posture

1.  **REST API Security**: Restrict port `8989` to `localhost`. Access via `maxctrl` locally.
2.  **Admin Credential Rotation**:
    ```bash
    maxctrl create user admin2 'StrongPassword!' --type=admin
    maxctrl destroy user admin
    ```
3.  **High Availability**: Deploy multiple MaxScale nodes behind a Virtual IP (Keepalived) or Load Balancer. Utilize cooperative monitoring to prevent split-brain failover scenarios.
4.  **Connection Pooling**: Ensure applications utilize connection pools to maximize MaxScale's multiplexing capabilities.
5.  **TLS/SSL**: Utilize `maxctrl reload tls` to rotate certificates without service interruption.

## 12. Diagnostics and Troubleshooting Matrix

| Symptom | Root Cause Analysis | Remediation Strategy |
| :--- | :--- | :--- |
| **Service fails to initialize** | Syntax errors in `/etc/maxscale.cnf` or invalid section definitions. | Execute `maxscale --config-check`. Review `journalctl -u maxscale -n 50`. |
| **Node State: `Down`** | MariaDB service stopped, firewall blocking port 3306, or `maxmon` authentication failure. | Verify `systemctl status mariadb`, check `firewall-cmd`, verify `maxmon` grants. |
| **Node State: `Running` (No Role)** | Replication broken, or Monitor lacks privileges to read replication state. | Execute `SHOW SLAVE STATUS\G`. Verify `REPLICATION CLIENT` grants. |
| **Access Denied (Port 4006)** | User missing, incorrect password, or host pattern mismatch. | Remember backend sees MaxScale IP. Ensure user allows `10.10.10.%` or `%`. |
| **Authentication Plugin Error** | MySQL 8 `caching_sha2_password` incompatibility. | Recreate user with `IDENTIFIED WITH mysql_native_password`. |
| **All Traffic Routes to Primary** | No healthy replicas, replication lag exceeds `max_slave_replication_lag`, or queries are wrapped in transactions. | Check `maxctrl list servers`. Verify replica lag. |
| **Stale Reads (Read-After-Write)** | Replication lag causing reads to hit unupdated replicas. | Enable `causal_reads=local` or execute reads within the same transaction block. |
| **Configuration Edits Ignored** | Runtime changes in `/var/lib/maxscale/maxscale.cnf.d/` override static file. | Clear runtime directory or use `maxctrl` for persistent runtime changes. |

**Diagnostic Commands:**
```bash
maxctrl list servers
maxctrl list monitors
sudo tail -n 50 /var/log/maxscale/maxscale.log
ss -tlnp | grep maxscale
```
