# Enterprise MariaDB and MaxScale Infrastructure Documentation
## Single-Node Architecture and Deep Database Concepts

This documentation details the architecture, implementation, and configuration of MariaDB MaxScale as an enterprise database proxy fronting a highly optimized Single-Node MariaDB deployment. It covers deep InnoDB storage engine concepts, Point-in-Time Recovery (PITR) strategies, deployment sequences, and integration with edge load balancers and reverse proxies.

Configuration directives and default behaviors are subject to change across software versions. Where version-specific parameters are critical, they are explicitly noted. Always cross-reference the [Official MariaDB Documentation](https://mariadb.com/docs) for the specific version deployed in your environment.

## 1. Architecture Overview and Core Components

### 1.1 Single-Node Enterprise Topology
In this architecture, MariaDB MaxScale functions as an enterprise-grade database proxy middleware fronting a single, highly-tuned MariaDB instance. Applications communicate with MaxScale using standard MySQL/MariaDB protocols. MaxScale abstracts the database endpoint, providing connection pooling, query routing logic, and a seamless migration path to a multi-node replication cluster in the future without requiring application code changes.

```text
                     [ Edge Load Balancer (HAProxy/Nginx) ]
                                  |
                                  | TCP/3306
                                  v
                     +------------------------+
                     |   MaxScale Proxy       |
                     |   10.10.10.203:4006    |
                     +------------------------+
                                  |
                                  | MySQL Protocol
                                  v
                     +------------------------+
                     |  MariaDB Single Node   |
                     |  10.10.10.201:3306     |
                     |  (InnoDB, WAL, PITR)   |
                     +------------------------+
```

### 1.2 Architectural Challenges Addressed

| Challenge | Architectural Solution |
| :--- | :--- |
| **Connection Exhaustion** | MaxScale multiplexes and pools connections, preventing the single MariaDB node from hitting `max_connections` limits during application traffic spikes. |
| **Topology Abstraction** | Applications connect to a single virtual IP/Port. The backend can be seamlessly transitioned to a Primary/Replica cluster later without modifying application connection strings. |
| **Security & Auditing** | Centralized authentication, IP whitelisting, and query filtering (e.g., QLA) occur at the proxy layer before reaching the database engine. |
| **Network Resilience** | MaxScale handles transient network drops, connection keepalives, and transaction replay, shielding the application from brief network anomalies. |

## 2. MaxScale Core Architecture

### 2.1 The Five Building Blocks
MaxScale configuration is object-oriented, relying on five core components:

| Object | Definition | Enterprise Function |
| :--- | :--- | :--- |
| **Server** | Defines a physical backend database instance (IP and Port). | Represents the actual data node (`10.10.10.201`). |
| **Monitor** | A daemon that continuously polls server health and state. | Detects node failures and triggers alerts or proxy-level mitigations. |
| **Router** | The logic engine that evaluates and directs incoming queries. | Executes Read/Write splitting logic or connection routing. |
| **Service** | Binds a Router to a specific set of Servers and Monitors. | Defines the logical proxy endpoint. |
| **Listener** | The network port and protocol exposed to client applications. | The ingress point for database traffic (`4006`). |

### 2.2 Routing Modules in a Single-Node Context

| Router Module | Behavior in Single-Node Topology | Future Scalability |
| :--- | :--- | :--- |
| `readwritesplit` | Analyzes SQL statements. Since only one node exists (marked as `Master`), **all** reads and writes are routed to `10.10.10.201`. | If replicas are added later, reads automatically distribute to them without config changes. |
| `readconnroute` | Assigns the backend server upon connection establishment. | Useful for dedicated analytics connections or simple connection pooling. |

## 3. Deep Database Concepts: InnoDB and Storage Internals

When deploying a Single Node MariaDB instance, deep understanding of the InnoDB storage engine is critical for enterprise performance, data integrity, and crash recovery.

### 3.1 InnoDB Buffer Pool and Memory Management
The InnoDB Buffer Pool is the primary memory area where InnoDB caches table and index data.
*   **Sizing**: For a dedicated single-node database server, `innodb_buffer_pool_size` should be configured to **70-80% of total system RAM**. This minimizes physical disk I/O by keeping the active working set in memory.
*   **LRU Algorithm**: The Buffer Pool uses a variant of the Least Recently Used (LRU) algorithm. It divides the pool into "new" and "old" sublists to prevent full-table scans from flushing out frequently accessed index pages (the "midpoint insertion strategy").
*   **Change Buffer**: Insert operations are buffered here if the target index page is not in the Buffer Pool. This merges random I/O into sequential I/O during background merges, drastically improving write performance for secondary indexes.

### 3.2 Write-Ahead Logging (WAL) and Redo Logs
InnoDB guarantees ACID compliance using Write-Ahead Logging.
*   **Mechanism**: Before modifying a data page in memory, InnoDB records the change to the Redo Log Buffer, which is then flushed to the physical Redo Log files (`ib_logfile0`, `ib_logfile1`) on disk.
*   **Crash Recovery**: In the event of a power failure or OS crash, MariaDB uses the Redo Logs during startup to apply any committed transactions that were not yet written to the main tablespace files, ensuring zero data loss for committed transactions.
*   **Tuning**: `innodb_log_file_size` and `innodb_log_files_in_group` must be balanced. Larger log files reduce checkpoint flush activity (improving write performance) but increase crash recovery time.

### 3.3 MVCC, Undo Logs, and Transaction Isolation
Multi-Version Concurrency Control (MVCC) allows read operations to proceed without locking rows being modified by other transactions.
*   **Undo Logs**: When a row is updated, the old version of the row is written to the Undo Log. Read queries access these historical versions to maintain a consistent snapshot of the database.
*   **Purge System**: A background thread continuously cleans up Undo Log entries once no active transactions require them. Proper sizing of the Undo Tablespace prevents transaction stalls during long-running analytical queries.

### 3.4 Binary Logging and Point-in-Time Recovery (PITR)
In a single-node architecture without replicas, the Binary Log is the sole mechanism for Point-in-Time Recovery.
*   **Format**: `binlog_format=ROW` is mandatory for enterprise environments. It logs the exact row changes rather than SQL statements, ensuring deterministic recovery and preventing replication issues if the topology is expanded later.
*   **GTID**: Global Transaction IDs (`gtid_strict_mode=1`) ensure every transaction has a unique, trackable identifier, simplifying backup restoration and future cluster scaling.

## 4. Licensing, Compatibility, and Ecosystem

*   **Business Source License (BSL)**: MaxScale 2.x and later operate under the BSL. Production use is free for a limited number of backend servers (typically up to two). Exceeding this requires a commercial subscription. Each version converts to GPL after its designated "Change Date". Consult the [Official MariaDB Documentation](https://mariadb.com/docs) for exact terms.
*   **Backend Compatibility**: MaxScale is fully optimized for MariaDB. While basic routing works with MySQL, MariaDB-specific extensions (like GTID management and advanced causal reads) are unsupported on MySQL backends.

## 5. Infrastructure Implementation Sequence

### 5.1 Network Topology and Node Provisioning

| Node Role | IP Address | Function |
| :--- | :--- | :--- |
| **DB1 (Single Node)** | `10.10.10.201` | Accepts all Read/Write operations, manages InnoDB storage. |
| **MaxScale Proxy** | `10.10.10.203` | Middleware proxy, exposes port `4006`, handles connection pooling. |

### 5.2 Single-Node MariaDB Deep Configuration
Execute on `10.10.10.201`.

**Base Installation (RHEL/AlmaLinux/Rocky):**
```bash
sudo dnf install mariadb-server -y
sudo systemctl enable --now mariadb
sudo mysql_secure_installation
```

**Core Configuration (`/etc/my.cnf.d/mariadb-server.cnf`):**
```ini
[mysqld]
bind-address      = 0.0.0.0
server_id         = 1
log_bin           = mariadb-bin
binlog_format     = ROW
gtid_strict_mode  = 1
expire_logs_days  = 7

# Deep InnoDB Tuning
innodb_buffer_pool_size = 12G # Adjust to 70-80% of total RAM
innodb_log_file_size    = 2G
innodb_log_buffer_size  = 64M
innodb_flush_log_at_trx_commit = 1 # Strict ACID compliance
innodb_flush_method     = O_DIRECT # Bypass OS cache to prevent double-buffering
innodb_file_per_table   = 1
innodb_io_capacity      = 2000 # Tune based on underlying storage IOPS
```

**Firewall Configuration:**
```bash
sudo firewall-cmd --permanent --add-port=3306/tcp
sudo firewall-cmd --reload
```

### 5.3 Identity and Access Management for Proxy Services
MaxScale requires dedicated service accounts to monitor health and authenticate clients. Execute on `10.10.10.201`.

```sql
-- 1. Monitor Account (Health checks)
CREATE USER 'maxmon'@'10.10.10.%' IDENTIFIED BY 'MonPass#123';
GRANT SUPER, RELOAD, PROCESS, SHOW DATABASES, EVENT ON *.* TO 'maxmon'@'10.10.10.%';
GRANT REPLICATION CLIENT, REPLICATION SLAVE ON *.* TO 'maxmon'@'10.10.10.%';

-- 2. Service Account (User authentication synchronization)
CREATE USER 'maxsvc'@'10.10.10.%' IDENTIFIED BY 'SvcPass#123';
GRANT SELECT ON mysql.user         TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.db           TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.tables_priv  TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.columns_priv TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.proxies_priv TO 'maxsvc'@'10.10.10.%';
GRANT SELECT ON mysql.roles_mapping TO 'maxsvc'@'10.10.10.%';
GRANT SHOW DATABASES ON *.* TO 'maxsvc'@'10.10.10.%';

-- 3. Application Account
CREATE USER 'appuser'@'%' IDENTIFIED BY 'AppPass#123';
GRANT ALL PRIVILEGES ON enterprise_db.* TO 'appuser'@'%';
```

### 5.4 MaxScale Proxy Installation
Execute on the MaxScale node (`10.10.10.203`):

```bash
curl -LsS https://r.mariadb.com/downloads/mariadb_repo_setup | sudo bash
sudo dnf install -y maxscale
sudo firewall-cmd --permanent --add-port=4006/tcp
sudo firewall-cmd --reload
```

### 5.5 MaxScale Configuration Management (Single-Node)
Backup the default configuration and define the enterprise topology.

```bash
sudo cp /etc/maxscale.cnf /etc/maxscale.cnf.original
sudo vim /etc/maxscale.cnf
```

**Baseline Configuration (`/etc/maxscale.cnf`):**
```ini
[maxscale]
threads=auto

[db1]
type=server
address=10.10.10.201
port=3306

[MariaDB-Monitor]
type=monitor
module=mariadbmon
servers=db1
user=maxmon
password=MonPass#123
monitor_interval=2s

[Read-Write-Service]
type=service
router=readwritesplit
servers=db1
user=maxsvc
password=SvcPass#123
# In a single-node setup, the only server is the Master.
# readwritesplit will route all traffic to the Master.

[Read-Write-Listener]
type=listener
service=Read-Write-Service
protocol=MariaDBClient
port=4006
```

**Password Encryption (Security Hardening):**
```bash
sudo maxkeys
sudo maxpasswd 'MonPass#123'
sudo maxpasswd 'SvcPass#123'
# Replace plain-text passwords in maxscale.cnf with the generated hashes.
sudo chmod 600 /etc/maxscale.cnf
sudo chown maxscale:maxscale /etc/maxscale.cnf
```

### 5.6 Service Initialization and State Verification
```bash
sudo systemctl enable --now maxscale
maxctrl list servers
```
*Expected State*: `db1` should report `Master, Running`.

## 6. Dynamic Configuration and Runtime Management

MaxScale supports dynamic reconfiguration via the `maxctrl` utility without requiring service restarts.

```bash
# Inspect State
maxctrl list servers
maxctrl list services
maxctrl list sessions

# Maintenance Mode (Useful before OS patching or backups)
maxctrl set server db1 maintenance   # Drains connections gracefully
maxctrl clear server db1 maintenance # Restores node to active pool
```
*Note*: Runtime changes made via `maxctrl` are persisted in `/var/lib/maxscale/maxscale.cnf.d/` and override static configurations in `/etc/maxscale.cnf`.

## 7. High Availability, Resilience, and Data Protection

In a single-node database architecture, High Availability (HA) relies on rapid recovery mechanisms and proxy redundancy rather than database-level failover.

### 7.1 Physical Backups with Mariabackup
Since there are no replicas, enterprise-grade physical backups are mandatory for PITR.
```bash
sudo dnf install mariadb-backup -y
mariabackup --backup --target-dir=/var/backup/full \
            --user=root --password=RootPass#123 \
            --parallel=4
```
*Recovery Strategy*: In the event of catastrophic failure, restore the `mariabackup` snapshot and apply binary logs up to the exact second of failure using `mysqlbinlog`.

### 7.2 MaxScale Proxy Redundancy
To prevent MaxScale from becoming a Single Point of Failure (SPOF), deploy a secondary MaxScale node (`10.10.10.204`) and place both behind an Edge Load Balancer (HAProxy/Nginx) utilizing a Virtual IP (VIP) via Keepalived.

## 8. Advanced Routing Parameters and Query Optimization

Apply these parameters to the `[Read-Write-Service]` section to optimize traffic and connection management.

| Parameter | Function |
| :--- | :--- |
| `max_connections=2000` | Limits total client connections to prevent proxy memory exhaustion. |
| `connection_keepalive=300s` | Sends keepalive packets to prevent firewalls from dropping idle connections. |
| `max_slave_connections=0` | Irrelevant in single-node, but ensures compatibility if replicas are added. |
| `master_accept_reads=true` | Explicitly allows the Master to serve reads (default behavior in single-node, but good for explicit documentation). |
| `transaction_replay=true` | Replays transactions interrupted by transient network errors between the proxy and the database. |

## 9. Query Filtering and Auditing

The Query Log All (QLA) filter is critical for enterprise auditing and debugging application-generated SQL.

```ini
[QLA]
type=filter
module=qlafilter
filebase=/var/log/maxscale/qla
log_type=unified

[Read-Write-Service]
# ... existing service config ...
filters=QLA
```
*Performance Note*: Filters introduce CPU overhead and disk I/O. Enable strictly for compliance, security auditing, or temporary debugging.

## 10. Edge Load Balancing and Reverse Proxy Integration

In enterprise environments, the MaxScale proxy layer is fronted by Layer 4 Load Balancers to ensure proxy high availability and distribute ingress traffic.

### 10.1 HAProxy TCP Load Balancing
HAProxy is the enterprise standard for raw TCP load balancing of database traffic.

```haproxy
global
    log /dev/log local0
    maxconn 8192
    daemon

defaults
    log     global
    mode    tcp
    option  tcplog
    timeout connect 5s
    timeout client  1h
    timeout server  1h

frontend maxscale_frontend
    bind *:3306
    default_backend maxscale_backend

backend maxscale_backend
    balance roundrobin
    option tcp-check
    server maxscale-node-1 10.10.10.203:4006 check inter 5s fall 3 rise 2
    # server maxscale-node-2 10.10.10.204:4006 check inter 5s fall 3 rise 2 (If HA is configured)
```

### 10.2 Nginx Stream Proxying
Nginx utilizes the `stream` module for high-performance TCP/UDP proxying.

```nginx
stream {
    upstream maxscale_backend {
        server 10.10.10.203:4006 max_fails=3 fail_timeout=10s;
    }

    server {
        listen 3306;
        proxy_pass maxscale_backend;
        proxy_timeout 1h;
        proxy_connect_timeout 10s;
    }
}
```

### 10.3 Apache HTTP Server Application-Tier Integration
*Architectural Note*: Apache HTTP Server is designed for HTTP/HTTPS reverse proxying. It is not suitable for raw TCP MySQL protocol proxying. The configuration below demonstrates the **Application-Tier** reverse proxy integration, routing secure web traffic to the application servers that subsequently query the MaxScale proxy.

```apache
<VirtualHost *:443>
    ServerName api.enterprise.local
    
    SSLEngine on
    SSLCertificateFile /etc/pki/tls/certs/server.crt
    SSLCertificateKeyFile /etc/pki/tls/private/server.key

    ProxyPreserveHost On
    
    # Route to Application Tier (which connects to MaxScale)
    ProxyPass / http://10.10.10.50:8080/ connectiontimeout=5 timeout=30
    ProxyPassReverse / http://10.10.10.50:8080/
    
    # Security Headers
    Header always set Strict-Transport-Security "max-age=63072000; includeSubDomains"
    Header always set X-Frame-Options "DENY"
    Header always set X-Content-Type-Options "nosniff"
</VirtualHost>
```

## 11. Production Hardening and Security Posture

1.  **REST API Security**: Restrict port `8989` to `localhost`. Access via `maxctrl` locally.
2.  **Admin Credential Rotation**:
    ```bash
    maxctrl create user admin_sec 'StrongPassword!' --type=admin
    maxctrl destroy user admin
    ```
3.  **TLS/SSL Encryption**: Enforce encrypted connections between the Application, MaxScale, and MariaDB using `maxctrl reload tls` and MariaDB `require_secure_transport`.
4.  **Filesystem Permissions**: Ensure `/etc/maxscale.cnf` and `/var/lib/maxscale/.secrets` are owned by `maxscale:maxscale` with `600` permissions.

## 12. Diagnostics and Troubleshooting Matrix

| Symptom | Root Cause Analysis | Remediation Strategy |
| :--- | :--- | :--- |
| **Service fails to initialize** | Syntax errors in `/etc/maxscale.cnf` or invalid section definitions. | Execute `maxscale --config-check`. Review `journalctl -u maxscale -n 50`. |
| **Node State: `Down`** | MariaDB service stopped, firewall blocking port 3306, or `maxmon` authentication failure. | Verify `systemctl status mariadb`, check `firewall-cmd`, verify `maxmon` grants. |
| **Access Denied (Port 4006)** | User missing, incorrect password, or host pattern mismatch. | Ensure backend user allows `10.10.10.%` or `%` since backend sees MaxScale IP. |
| **Authentication Plugin Error** | MySQL 8 `caching_sha2_password` incompatibility (if using MySQL backend). | Recreate user with `IDENTIFIED WITH mysql_native_password`. |
| **Connection Drops Idle** | Intermediate firewalls dropping idle TCP sessions. | Enable `connection_keepalive=300s` in MaxScale service config. |
| **Configuration Edits Ignored** | Runtime changes in `/var/lib/maxscale/maxscale.cnf.d/` override static file. | Clear runtime directory or use `maxctrl` for persistent runtime changes. |

**Diagnostic Commands:**
```bash
maxctrl list servers
maxctrl list monitors
sudo tail -n 50 /var/log/maxscale/maxscale.log
ss -tlnp | grep maxscale
```
