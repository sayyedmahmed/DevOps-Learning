# MaxScale + Single MariaDB Node — Complete Lab Guide

One MariaDB server behind MaxScale. No replica. Learn the config,
the objects, the client path, and how to diagnose auth errors.

```
 Client --> MaxScale (10.10.10.190:4006) --> MariaDB (10.10.10.201:3306)
```

IPs used here: MaxScale `10.10.10.190`, MariaDB `10.10.10.201`.
Replace with yours. Commands for AlmaLinux / RHEL / Rocky.

---

## 1. Prepare MariaDB (10.10.10.201)

### 1.1 Install
```bash
sudo dnf install mariadb-server -y
mariadb --version
```

### 1.2 Server config
```bash
sudo vim /etc/my.cnf.d/mariadb-server.cnf
```
Under `[mysqld]`:
```ini
bind-address      = 0.0.0.0
server_id         = 1
log_bin           = mariadb-bin
binlog_format     = ROW
log_slave_updates = ON
binlog_expire_logs_seconds = 604800
report_host       = 10.10.10.201
```

```bash
sudo systemctl enable --now mariadb
sudo firewall-cmd --permanent --add-port=3306/tcp
sudo firewall-cmd --reload
```

Verify:
```sql
SHOW VARIABLES LIKE 'server_id';    -- 1
SHOW VARIABLES LIKE 'log_bin';      -- ON
```

### 1.3 Create the MaxScale users

> One user for both monitor and service (guide uses `maxmon`+`maxsvc`;
> we collapse into `max`). Grant **everything** both roles need.

```bash
mariadb --skip-ssl -u root -p
```

```sql
-- Monitor privileges (REPLICA MONITOR required on 10.5.9+ incl. 10.11/11.x)
CREATE USER 'max'@'10.10.10.%' IDENTIFIED BY '123';
GRANT REPLICA MONITOR ON *.*             TO 'max'@'10.10.10.%';

-- Service privileges (read the account list)
GRANT SELECT ON mysql.user               TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.global_priv        TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.db                 TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.tables_priv        TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.columns_priv       TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.proxies_priv       TO 'max'@'10.10.10.%';
GRANT SELECT ON mysql.roles_mapping      TO 'max'@'10.10.10.%';
GRANT SHOW DATABASES ON *.*              TO 'max'@'10.10.10.%';

-- App user for client testing
CREATE DATABASE labtest;
CREATE USER 'appuser'@'%' IDENTIFIED BY 'AppPass#123';
GRANT ALL PRIVILEGES ON labtest.* TO 'appuser'@'%';

FLUSH PRIVILEGES;
```

**Important:** Do **not** also create `'max'@'10.10.10.190'`.
MariaDB matches the most specific host, so a `.190` row will shadow
the `%` row and may have different grants/password → `Auth Error`.
Only `'max'@'10.10.10.%'` should exist.

Verify:
```sql
SELECT user, host FROM mysql.user WHERE user='max';
-- exactly one row: max | 10.10.10.%
```

## 2. Prepare MaxScale host (10.10.10.190)

### 2.1 Install
```bash
curl -LsS https://r.mariadb.com/downloads/mariadb_repo_setup | sudo bash
sudo dnf install -y maxscale
maxscale --version
sudo firewall-cmd --permanent --add-port=4006/tcp
sudo firewall-cmd --reload
```

### 2.2 Stop the MariaDB client from requiring TLS (lab shortcut)

The MariaDB client on 190 defaults to requiring TLS, but 201 has no
certs. Any plaintext connection fails with:
```
ERROR 2026: SSL is required, but the server does not support it
```
MaxScale's monitor uses the same client library and hits the same wall.

**Lab fix** — tell the client not to require TLS:
```bash
sudo tee /etc/my.cnf.d/zz-no-ssl.cnf >/dev/null <<'EOF'
[client]
ssl=0
EOF
```

Test:
```bash
mariadb -h 10.10.10.201 -u max -p -e "SELECT 1"
```
Should return `1` with no TLS error.

> **Production:** instead add `ssl_cert`/`ssl_key` to `[mysqld]` on 201
> (and `ssl_ca` on both sides). Never ship plaintext DB traffic.

### 2.3 Write the MaxScale config

```bash
sudo cp /etc/maxscale.cnf /etc/maxscale.cnf.original
sudo vim /etc/maxscale.cnf
```

```ini
[maxscale]
threads=auto

[mariadb-1]
type=server
address=10.10.10.201
port=3306

[MariaDB-Monitor]
type=monitor
module=mariadbmon
servers=mariadb-1
user=max
password="123"
monitor_interval=2s

[Read-Write-Service]
type=service
router=readwritesplit
cluster=MariaDB-Monitor
user=max
password="123"

[Read-Write-Listener]
type=listener
service=Read-Write-Service
protocol=MariaDBClient
port=4006
```

**Password quoting matters:** `password=123` is parsed as a JSON integer
and dropped; `password="123"` is a string and works. Always quote.

### 2.4 Remove any leftover secrets file

```bash
sudo systemctl stop maxscale
sudo ls -la /var/lib/maxscale/.secrets 2>/dev/null && \
    sudo mv /var/lib/maxscale/.secrets /var/lib/maxscale/.secrets.bak
```

If `.secrets` exists, MaxScale runs in **encrypted-password mode** and
treats your plaintext `"123"` as an encrypted blob → decryption fails →
monitor sends **no password** → `(using password: NO)` → `Auth Error`.
Removing it returns MaxScale to plaintext mode.

> **Production alternative:** keep `.secrets` and encrypt passwords:
> ```bash
> sudo maxkeys
> sudo maxpasswd 123          # prints a hex string
> ```
> Paste the hex into `password=` (unquoted) and restart.
> Mixing `.secrets` + plaintext password = the failure mode above.

### 2.5 Check and start

```bash
sudo -u maxscale maxscale --config-check
sudo systemctl start maxscale
sleep 5
maxctrl list servers
```

Expect:
```
│ mariadb-1 │ 10.10.10.201 │ 3306 │ 0 │ Master, Running │ ... │
```

## 4. Auth error reference — every failure mode and its fix

This section is the point of the document. If `maxctrl list servers`
shows `Auth Error, Down`, work through this table.

| Log line | Root cause | Fix |
|---|---|---|
| `TLS/SSL error: SSL is required, but the server does not support it` (from `mariadb` CLI) | Client default demands TLS; server has none | `[client] ssl=0` in `/etc/my.cnf.d/zz-no-ssl.cnf` (lab), or enable `ssl_cert`/`ssl_key` on server |
| `Access denied … (using password: NO)` | No password reached MariaDB | See the three causes below |
| `Access denied … (using password: YES)` | Password reached MariaDB but was rejected | Wrong password on the matched host row; or missing grants |
| `maxctrl alter … Expected a json string, but got a json integer` | `password=123` parsed as integer | `password='"123"'` on CLI, `password="123"` in file |
| Duplicate `'max'@'10.10.10.190'` and `'max'@'10.10.10.%'` | Most-specific host wins; wrong row has wrong grants/password | `DROP USER 'max'@'10.10.10.190';` |
| `Using encrypted passwords. Encryption key read from '/var/lib/maxscale/.secrets'` followed by `(using password: NO)` | `.secrets` present + plaintext password in cnf | Move `.secrets` aside (plaintext mode), or run `maxpasswd` and paste the hex |
| `REPLICA MONITOR` grant missing | `mariadbmon` needs it even with a single server | `GRANT REPLICA MONITOR ON *.* TO 'max'@'10.10.10.%';` |

### Diagnostic sequence (paste these, don't guess)

**On MaxScale (190):**
```bash
maxctrl list servers
maxctrl show monitor MariaDB-Monitor | grep -iE 'user|password'
sudo tail -n 30 /var/log/maxscale/maxscale.log | grep -iE 'access denied|auth|error'
sudo ls -la /var/lib/maxscale/.secrets
sudo cat /var/lib/maxscale/maxscale.cnf.d/* 2>/dev/null    # live overrides
```

**On MariaDB (201):**
```sql
SELECT user, host, plugin, ssl_type, authentication_string
FROM mysql.user WHERE user='max';
SHOW GRANTS FOR 'max'@'10.10.10.%';
```

**Direct test mimicking MaxScale's connection (from 190):**
```bash
mariadb --skip-ssl -h 10.10.10.201 -u max -p123 -e "SHOW SLAVE STATUS"
```
- Works → grants are fine, problem is MaxScale config (password / `.secrets`).
- `Access denied` → the error names the missing privilege.

### What "correct" looks like

**Password hash for `123`** is `*23AE809DDACAF96AF0FD78ED04B6A265E05AA257`.
If your `authentication_string` differs, the password isn't `123`.

**`maxctrl show monitor MariaDB-Monitor | grep password`** should show
`"password": "*****"` — not empty, not null.

**`/var/lib/maxscale/.secrets`** should **not exist** in plaintext mode.

**`maxctrl list servers`** should show `Master, Running`, not `Auth Error, Down`.

## 5. Stage 2 experiments (single server)

1. **Stop MariaDB**
   ```bash
   # on 201
   sudo systemctl stop mariadb
   # on 190
   maxctrl list servers           # Down within ~2s
   sudo systemctl start mariadb   # on 201
   maxctrl list servers           # back to Master, Running
   ```

2. **Wrong monitor password**
   ```bash
   maxctrl alter monitor MariaDB-Monitor password='"wrong"'
   maxctrl list servers           # Down
   maxctrl alter monitor MariaDB-Monitor password='"123"'
   ```

3. **Inspect what MaxScale really uses**
   ```bash
   maxctrl show monitor MariaDB-Monitor
   maxctrl show service Read-Write-Service
   maxctrl show maxscale
   ```

4. **Live-change storage**
   ```bash
   ls -la /var/lib/maxscale/maxscale.cnf.d/
   ```
   `maxctrl alter` saves here; these files override `/etc/maxscale.cnf`.

5. **Change listener port**
   ```bash
   sudo systemctl stop maxscale
   sudo vim /etc/maxscale.cnf   # port=4006 -> 4010
   sudo systemctl start maxscale
   ss -tlnp | grep maxscale
   # change back to 4006, restart
   ```

## 6. Cheat sheet

```
FILES
  /etc/maxscale.cnf                   main config
  /var/lib/maxscale/maxscale.cnf.d/   live overrides (win over main file)
  /var/lib/maxscale/.secrets          encrypted-password mode toggle
  /var/log/maxscale/maxscale.log      log
  /etc/my.cnf.d/zz-no-ssl.cnf         client TLS override (lab)

INSPECT
  maxctrl list servers | services | listeners | monitors | sessions
  maxctrl show server NAME | service NAME | monitor NAME | maxscale

CHECK CONFIG
  sudo -u maxscale maxscale --config-check

LIVE CHANGES
  maxctrl alter service Read-Write-Service max_slave_replication_lag=10s
  maxctrl alter monitor MariaDB-Monitor password='"123"'
  maxctrl create server NAME IP PORT
  maxctrl link monitor MariaDB-Monitor NAME
  maxctrl set server NAME maintenance
  maxctrl clear server NAME maintenance
  maxctrl reload service Read-Write-Service

REMEMBER
  1. Objects refer by name: listener -> service -> monitor -> server
  2. cluster=<monitor> = use whatever that monitor watches
  3. MaxScale connects from ITS OWN IP, not the client's
  4. Password must be quoted: "123" not 123
  5. If .secrets exists, passwords must be maxpasswd output
  6. One 'max' user only, wildcard host, no specific-IP duplicate
```

## 7. When you're ready for a replica (out of scope, pointer only)

You do **not** need this now. When you add db2:
- Build db2 with `server_id=2`, `read_only=ON`, same `log_bin`/`binlog_format`/`log_slave_updates`.
- `CREATE USER 'repl'@'10.10.10.%'` on 201; `CHANGE MASTER TO … MASTER_USE_GTID=slave_pos` on db2.
- On 190: `maxctrl create server mariadb-2 10.10.10.202 3306` then `maxctrl link monitor MariaDB-Monitor mariadb-2`.
- The service and listener do **not** change.
