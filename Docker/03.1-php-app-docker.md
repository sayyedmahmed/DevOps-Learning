# PHP Application Container Deployment

Single-container deployment for the PHP + Nginx + PHP-FPM stack described in `PHP on AlmaLinux with Nginx`. No Docker Compose. Uses Supervisor to run both services inside one image.

## 1. Project layout

```
php-docker/
├── Dockerfile
├── nginx.conf
├── supervisord.conf
└── src/
    ├── index.php
    └── style.css
```

`src/` contains the same files from the native setup. `index.php` and `style.css` are unchanged.

## 2. Changes from the native setup

| Native | Container | Reason |
|---|---|---|
| `dnf install nginx php php-fpm` on host | `RUN dnf install ...` in Dockerfile | Baked into the image |
| Web root `/usr/share/nginx/html` | `/var/www/html` | Docker convention, shorter path |
| Nginx runs as `apache` | `nginx` | Container-specific user, set in `nginx.conf` |
| PHP-FPM runs as `apache` | `nginx` | Same user for both, no socket permission mismatch |
| PHP-FPM on unix socket `/run/php-fpm/www.sock` | TCP `127.0.0.1:9000` | Simpler inside a container, no file permissions to manage |
| Site config in `/etc/nginx/conf.d/php-app.conf` | Full `nginx.conf` replaces `/etc/nginx/nginx.conf` | One file copy removes the default server block. No vim, no sed on `nginx.conf` |
| Delete default server block with vim | Handled by the copied `nginx.conf` | Config lives in the repo, version controlled |
| `setsebool` and `restorecon` for SELinux | Not needed | Containers run isolated, no SELinux context on internal sockets |
| `firewall-cmd --add-service=http` | Not needed inside the image | Port mapping via `-p` on `docker run` |
| `systemctl enable --now` to start services | `supervisord` | No systemd inside the container |
| `chown -R apache:apache` on files | `chown -R nginx:nginx` in Dockerfile | Same idea, different user |

What stays the same: the application files, the socket handoff between Nginx and PHP-FPM, and the request flow.

## 3. Dockerfile

```dockerfile
FROM almalinux:9

RUN dnf install -y epel-release && \
    dnf install -y nginx php php-fpm php-cli supervisor && \
    dnf clean all

WORKDIR /var/www/html

COPY src/ /var/www/html/
COPY nginx.conf /etc/nginx/nginx.conf
COPY supervisord.conf /etc/supervisord.conf

RUN sed -i 's/^user = .*/user = nginx/' /etc/php-fpm.d/www.conf && \
    sed -i 's/^group = .*/group = nginx/' /etc/php-fpm.d/www.conf && \
    sed -i 's|^listen = .*|listen = 127.0.0.1:9000|' /etc/php-fpm.d/www.conf && \
    chown -R nginx:nginx /var/www/html

EXPOSE 80

CMD ["/usr/bin/supervisord", "-c", "/etc/supervisord.conf"]
```

Line by line:

- `FROM almalinux:9` matches the OS you tested on. Same package names, same defaults.
- `RUN dnf install ...` installs the four programs the native setup used, plus `supervisor` to run two services in one container.
- `dnf clean all` removes cache, keeps the image small.
- `WORKDIR /var/www/html` sets the web root. Same role as `/usr/share/nginx/html` in the native setup.
- `COPY src/` brings the app files in. `COPY nginx.conf` and `COPY supervisord.conf` bring the configs in.
- The `sed` block matches the native changes you made by hand: change PHP-FPM user to `nginx`, change its listen address to `127.0.0.1:9000`, and fix file ownership.
- `EXPOSE 80` documents the internal port. Actual mapping happens on `docker run`.
- `CMD` starts Supervisor, which starts Nginx and PHP-FPM.

## 4. nginx.conf

Replaces `/etc/nginx/nginx.conf` entirely. This is what removes the default server block: you are not editing in place, you are shipping the correct config from the start.

```nginx
user nginx;
worker_processes auto;
error_log /var/log/nginx/error.log notice;
pid /run/nginx.pid;

include /usr/share/nginx/modules/*.conf;

events {
    worker_connections 1024;
}

http {
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';

    access_log /var/log/nginx/access.log main;

    sendfile on;
    tcp_nopush on;
    keepalive_timeout 65;
    types_hash_max_size 4096;

    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    server {
        listen 80 default_server;
        server_name _;
        root /var/www/html;
        index index.php index.html;

        location / {
            try_files $uri $uri/ /index.php;
        }

        location ~ \.php$ {
            try_files $uri =404;
            fastcgi_pass 127.0.0.1:9000;
            fastcgi_index index.php;
            include fastcgi_params;
            fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        }
    }
}
```

Differences from the native `php-app.conf`:

- `user nginx;` at the top instead of `user apache;`.
- The `server { ... }` block is inline in `http { }`. No `include /etc/nginx/conf.d/*.conf;` because there are no other site files.
- `fastcgi_pass 127.0.0.1:9000` instead of `unix:/run/php-fpm/www.sock`. TCP loopback is simpler inside a container. If the socket file is missing or misconfigured, the failure mode is cleaner.
- `root /var/www/html` matches the Dockerfile.

Everything else (`try_files`, `SCRIPT_FILENAME`, `index`) is identical to the native version.

## 5. supervisord.conf

```ini
[supervisord]
nodaemon=true
logfile=/var/log/supervisord.log
pidfile=/var/run/supervisord.pid

[program:php-fpm]
command=/usr/sbin/php-fpm -F
autostart=true
autorestart=true
stdout_logfile=/dev/stdout
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr
stderr_logfile_maxbytes=0

[program:nginx]
command=/usr/sbin/nginx -g "daemon off;"
autostart=true
autorestart=true
stdout_logfile=/dev/stdout
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr
stderr_logfile_maxbytes=0
```

- `[supervisord] nodaemon=true` keeps Supervisor in the foreground, which is required for the container to stay alive.
- `[program:php-fpm]` runs PHP-FPM. `-F` means foreground, so Supervisor can track it.
- `[program:nginx]` runs Nginx. `-g "daemon off;"` overrides Nginx's default background mode so Supervisor can track it.
- `stdout_logfile=/dev/stdout` forwards service logs to the container's stdout. `docker logs php-app` shows everything, same as `journalctl` or `tail -f` on the host.
- `autorestart=true` restarts a service if it crashes. Behavior similar to `systemd`'s `Restart=on-failure`.

## 6. Application files

`src/index.php` and `src/style.css` are copied from the native setup unchanged. The native troubleshooting that touched Nginx and SELinux does not affect them.

## 7. Build

From inside `php-docker/`:

```bash
docker build -t php-app .
```

- `-t php-app` tags the image with a name you can reference later.
- `.` is the build context. Everything in the current directory is sent to the Docker daemon, minus anything listed in `.dockerignore`.

Optional `.dockerignore` in the same folder:

```
.git
*.md
```

Keeps the build context small. Not required, just tidy.

## 8. Run

```bash
docker run -d --name php-app -p 80:80 php-app
```

- `-d` runs detached (in the background).
- `--name php-app` names the container so you can refer to it later.
- `-p 80:80` maps host port 80 to container port 80.
- `php-app` is the image name from the build step.

If host Nginx is still running on port 80, this fails with `port is already allocated`. Stop it first:

```bash
sudo systemctl stop nginx
sudo systemctl disable nginx
```

The container replaces host Nginx now.

## 9. Verify

```bash
docker ps
docker logs php-app
curl -I http://localhost/
```

Expected:

- `docker ps` shows the container running.
- `docker logs php-app` shows Nginx and PHP-FPM start lines from Supervisor.
- `curl -I` returns `HTTP/1.1 200 OK` with `Content-Type: text/html; charset=UTF-8`.

Open `http://<vm-ip>/` in a browser. The PHP app loads.

## 10. Rebuild after editing app files

Files are baked into the image. Editing `src/index.php` on the host does nothing until you rebuild and restart:

```bash
docker rm -f php-app
docker build -t php-app .
docker run -d --name php-app -p 80:80 php-app
```

`docker rm -f` stops and removes the old container in one step. The old image stays as a previous layer until you run `docker image prune`.

To avoid rebuilding every time, mount the source as a volume instead:

```bash
docker run -d --name php-app -p 80:80 -v "$(pwd)/src:/var/www/html" php-app
```

Now editing `src/index.php` on the host appears inside the container immediately. This is the container equivalent of copying files to `/usr/share/nginx/html` during daily usage.

## 11. Stop and clean up

```bash
docker stop php-app
docker rm php-app
docker rmi php-app
```

- `stop` sends SIGTERM, Supervisor shuts down both services gracefully.
- `rm` removes the container.
- `rmi` removes the image.

## 12. Troubleshooting

| Symptom | Likely cause | Check |
|---|---|---|
| Container exits immediately | One service fails to start | `docker logs php-app` |
| `port is already allocated` | Host Nginx still on port 80 | `sudo systemctl stop nginx` |
| `502 Bad Gateway` | PHP-FPM not reachable on `127.0.0.1:9000` | `docker exec php-app ss -ltnp` |
| `403 Forbidden` | Wrong owner on `/var/www/html` | `docker exec php-app ls -l /var/www/html` |
| `404 Not Found` | Wrong `root` in `nginx.conf` | `docker exec php-app grep root /etc/nginx/nginx.conf` |
| PHP shown as plain text | Nginx not forwarding to PHP-FPM | `docker exec php-app grep fastcgi_pass /etc/nginx/nginx.conf` |
| Config syntax error at build | Typo in `nginx.conf` | `docker run --rm php-app nginx -t` |

Useful commands:

```bash
docker logs php-app                    # both services, live
docker exec -it php-app sh             # shell inside the container
docker exec php-app nginx -t           # check nginx config syntax
docker exec php-app ss -ltnp           # listening ports inside the container
```

`docker exec` runs a command inside the running container. `-it` gives an interactive shell. This replaces `ssh` for container debugging.

## 13. Why some native steps disappear

- **SELinux and firewalld** are configured per OS. Inside the container there is no enforcing SELinux context for the Nginx to PHP-FPM handoff, and no host firewall in front of loopback. The host's firewalld still exists, but Docker manages the `-p` port forwarding through iptables and firewalld does not see those rules the same way.
- **`systemctl`** is not present in the container. Supervisor fills that role.
- **`chown`** still matters, just with the `nginx` user instead of `apache`.
- **`nginx -t`** still matters, just run via `docker exec`.

## 14. Quick rebuild from scratch

```bash
# 1. Prepare files
mkdir -p php-docker/src
# add Dockerfile, nginx.conf, supervisord.conf, and src/index.php + style.css

# 2. Stop host nginx to free port 80
sudo systemctl stop nginx

# 3. Build and run
cd php-docker
docker build -t php-app .
docker run -d --name php-app -p 80:80 php-app

# 4. Verify
docker ps
docker logs php-app
curl -I http://localhost/
```

If `docker ps` shows the container up and `curl -I` returns `200 OK`, the container deployment is complete and matches the native behavior.
